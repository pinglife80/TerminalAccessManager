# 非合规终端网段真实性核验计划

> 文档版本：r1  更新日期：2026-08-24

## 1. 摘要（结论先行）

针对「当前非合规且封锁终端全部在 10.8.11.0/24，其它终端是否真的都合规」这一疑问，核验结论如下：

1. **「全部非合规终端集中在 10.8.11.0/24」这一现象是真实的**，但它是**配置 + 数据双重作用的结果**，不是统计口径 bug，也不是"只有这一个网段在检测"。
2. **「其它终端都合规」这一认知不准确**：其余 1151 台终端里，只有 **393 台是真正「合规(compliant)」**（经 IPGuard 基线校验通过），另外 **758 台是「白名单豁免(bypass)」**（整段网段被加白名单，根本没经过合规校验），二者性质完全不同。
3. 核验中进一步发现 **3 处潜在风险点**（详见第 4 节），需要人工关单，但均非代码缺陷。

## 3. 根因分析（为什么非合规只出现在 10.8.11）

1. **白名单把大片网段整体豁免**：`10.8.0.0/21`、`10.8.24.0/21` 等规则覆盖了 10.8.2\~10.8.7、10.8.8、10.8.9、10.8.10、10.8.24\~10.8.31，这些网段的 758 台终端直接 `bypass`，**不参与合规校验**。
2. **10.8.11.0/24 是唯一配置了** **`ip_cidr`** **scope 的用户网段**：命中后采用「仅 IP 匹配」策略——只要 IP 不在 IPGuard 基线里就判 `non_compliant`。
3. **其余用户网段（10.8.12\~10.8.22）用「IP+MAC 双重匹配」**，当前这些网段的终端恰好全部在 IPGuard 基线中匹配成功，因此暂时没有非合规终端。
4. 结论：**非合规集中在 10.8.11 不是"检测只覆盖这一个网段"，而是「白名单豁免了大部分网段 + 10.8.11 里存在 11 个 IP 未在 IPGuard 登记的终端」** 共同导致的现象。

## 4. 发现的风险点（需人工关单，非代码 bug）

### 风险点 A：3 台终端的 MAC 已登记在 IPGuard，但对应 IP 是"外网/VPN 网段"

11 台非合规终端中，3 台的 MAC 在 IPGuard 基线里确实存在，只是登记的 IP 是其它网段：

| 终端当前(ARP)                       | IPGuard 登记 IP  | 说明        |
| ------------------------------- | -------------- | --------- |
| 10.8.11.26 / C0:3C:59:01:9B:8B  | 10.8.119.15    | 外网/VPN 网段 |
| 10.8.11.40 / 10:6F:D9:A0:F2:73  | 192.168.43.6   | VPN 网段    |
| 10.8.11.199 / 38:D5:7A:44:69:4B | 192.168.70.205 | VPN 网段    |

这 3 台设备在 IPGuard 里是合法的，但 IPGuard 上报的是 VPN/副接口 IP，而非其在 10.8.11 的真实 LAN IP；叠加 10.8.11 的「仅 IP 匹配」策略，导致其 LAN IP 被判 `non_compliant`。**存在误封可能，需人工确认**（确属合法设备则加白名单，或修正 IPGuard 基线数据）。

### 风险点 B：11 台非合规终端均为"陈旧记录"

11 台非合规终端 `timestamp` 全部停在 8/19\~8/21（最近 3\~5 天 ARP 未再发现），但黑名单与防火墙封锁仍有效（对账结果 `firewall_ip_count=11 = db_entry_count=11`）。疑似已销毁/离线的 VM 幽灵记录，**建议确认是否仍真实存在，若已下线则清理终端记录 + 黑名单 + 防火墙解封**。

### 风险点 C：758 台「bypass」≠「合规」

前端页面将 `bypass` 与 `compliant` 分开展示，但需注意：**758 台 bypass 是"白名单豁免"，从未经过合规校验**，不能等同于"合规"。若业务上对「整体合规率」有统计，应按 `compliant / (compliant + non_compliant)` 而不是把 bypass 算作合格。

## 5. 假设与决策

* 本次核验为**只读诊断**，不修改任何代码、不修改任何数据。

* 判定逻辑（白名单优先 → scope 定策略 → IPGuard 匹配）本身**无缺陷**，风险点 A/B 属于**数据质量问题**（IPGuard 基线 IP 漂移、ARP 陈旧记录），需业务侧关单。

* 本文档不涉及代码变更，因此不触发 `./manage.sh update`。

## 6. 建议的下一步（可选项，需业务确认后执行）

按优先级排序，均需人工确认后再动手：

1. **核验 3 台 MAC 漂移终端**（风险点 A）：确认为合法设备则在其接入网段加入白名单或修正 IPGuard 基线；确认为非法则维持封锁。
2. **核验 11 台陈旧终端**（风险点 B）：ping/ARP 确认是否仍在线；已下线则删除终端记录并同步解封防火墙。
3. **复核整段白名单策略**（风险点 C）：确认 `10.8.0.0/21`、`10.8.24.0/21` 等大网段豁免是否符合预期。

## 7. 验证步骤（若执行任一项处置后）

1. `docker exec tam_db psql -U tam_admin -d tam_db -c "SELECT compliance_status,status,count(*) FROM terminals GROUP BY 1,2;"` 确认数量变化符合预期。
2. 触发一次对账：`POST /api/v1/system/firewall-reconciliation`（或等待定时对账），确认 `reconcile:latest` 的 `firewall_ip_count == db_entry_count` 且 `firewall_errors=[]`。
3. 终端管理页确认 `non_compliant+blocked`、黑名单页、防火墙实际状态三者一致。
