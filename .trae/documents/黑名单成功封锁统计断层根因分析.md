## 一、结论（摘要）

终端管理页存在「`compliance_status='non_compliant'` 且 `status='blocked'` 的终端」（且防火墙实际已封锁），但黑名单管理页「成功封锁（success_blocked）」分类统计里看不到这些条目，**根因是系统对「活跃封锁」这一概念存在两套互斥的定义（口径分裂）**：

- **统计/列表/看板**：判定「活跃封锁」= `auto_unblocked=False AND unblocked_at IS NULL AND (expires_at >= now OR expires_at IS NULL)`（**要看 `expires_at`**）。
- **对账自愈背书**：判定「终端的 blocked 是否有 blacklist 背书」= `auto_unblocked=False AND unblocked_at IS NULL`（**不看 `expires_at`**）。

当一条封锁的 `expires_at` 刚到期、但尚未被 `cleanup_expired_blacklist` 解封时（解封延迟/失败/任务被暂停），该条目会落入一个「三分类之外的孤儿窗口」：

1. 对账 `_repair_stale_terminal_status` 认为它「仍有背书」（`unblocked_at IS NULL`），**不会**把终端自愈为 unblocked → 终端保持 `blocked`；
2. 但它又不满足统计侧的 `expires_at >= now` → 被排除在 `success_blocked` 之外；
3. 同时它未解封（不满足 `success_unblocked`）、也不满足 `pending_retry_unblock`（同为 active filter）。

于是：**终端 blocked，黑名单页却统计不到它**。

### 2.3 过期清理链路（负责收敛窗口）

- [cleanup_expired_blacklist()](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py#L104-L124) 后台任务每 `scheduler_firewall_query_interval`（默认 300s）运行，受暂停开关 + Redis 分布式锁保护。
- [TerminalService.cleanup_expired_blacklist()](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1885-L2051)：查询 `expires_at < now AND auto_unblocked=False` → 调 `sangfor.unblock_ip()` 解封 → 成功则 `unblocked_at` 落库 + 恢复终端；失败则 `expires_at` 延后 30 分钟重试。

因此，只要该任务正常运行，过期条目通常会在数分钟内被解封并移入 `success_unblocked`，窗口极短。**断层会"持续"暴露，说明清理任务未能及时处理过期条目**（见下文 §三）。

## 三、根因分解

### 根因 1（直接）：`success_blocked` 的 active filter 用 `expires_at` 过滤

[get_blacklist_stats()](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1630-L1646) 中：

```python
active_filter = and_(
    Blacklist.auto_unblocked == False,
    Blacklist.unblocked_at.is_(None),
    or_(Blacklist.expires_at >= _now, Blacklist.expires_at.is_(None)),
)
success_blocked = count(Blacklist.id) where active_filter
```

`expires_at < now` 的条目被排除 → 已过期条目在 `success_blocked` 不计数。

### 根因 2（放大器）：对账自愈「不看 expires_at」，不回收过期窗口

[`_repair_stale_terminal_status`](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/firewall_reconciliation_service.py#L195-L220) 的 `active_bl` 判定**不含 `expires_at`**。所以即使条目过期，终端仍被认定为「有背书」，`status='blocked'` 保持不变。二者叠加，形成「终端 blocked，黑名单统计缺失」的稳定断层。

### 根因 3（持续性来源）：清理任务未及时解封过期条目

断层是否长期存在，取决于 `cleanup_expired_blacklist` 的收敛能力。以下场景会导致过期条目长期残留：

1. 任务被暂停（`scheduler:ctrl:firewall_query` 置为 `paused`）。
2. 分布式锁被另一实例长期占用（`scheduler:lock:firewall_query`）。
3. 防火墙解封持续失败（禁用/缺失/API 报错）→ 每条都 `expires_at = now + 30min` 反复重试。
4. 多防火墙场景下部分解封失败，导致条目卡在重试循环。

### 根因 4（语义混淆）：`success_blocked` 命名与实际含义偏差

字段名暗示「成功封锁」（blocks that succeeded on firewall），但实现从不校验 `last_operation_status == 'success'`（字段存在但未用），也不校验防火墙实际状态，仅用 DB 软状态 + `expires_at` 近似「仍在封锁期内」。这让"为什么防火墙封锁成功却统计不到"的困惑被放大。

## 四、建议修复方向（本次不改代码，供后续决策）

用户已确认修复方向为「**两者都做**」：

### 方向 A：统一「活跃封锁」口径（消除统计断层）

将「活跃封锁」的口径统一为「以解封时间为唯一事实」，去掉 `expires_at` 过滤：

- 改 [get_blacklist_stats](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1630-L1646)、[get_blacklist](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1444-L1451)、`get_blacklist_count`、[get_stats.blocked](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L291-L300)、[`_get_db_active_blacklist_by_firewall`](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/firewall_reconciliation_service.py#L270-L278) 五处的 active filter 统一为：

```python
Blacklist.auto_unblocked == False,
Blacklist.unblocked_at.is_(None),
```

- 效果：过期未解封条目在四处统计/列表/看板都能看到，与终端 `blocked` 状态对齐；与对账背书口径（已不看 `expires_at`）也保持一致。
- 若需区分「已过期」状态，建议**新增显式分类**（如 `pending_cleanup` / `expired`），而不是让条目在三分类之外"隐身"。

### 方向 B：保障清理及时性（窗口收敛）

- 排查 [cleanup_expired_blacklist](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1885-L2051) 长期不收敛的原因（暂停/锁/解封失败循环）。
- 对「持续解封失败」的过期条目增加告警/兜底，避免无限 `+30min` 重试淹没。
- 保持对账侧「不看 `expires_at`」的防震荡设计不变（这是正确的），只统一统计侧口径，避免回到震荡。
