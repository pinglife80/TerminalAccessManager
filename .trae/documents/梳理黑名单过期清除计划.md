# 黑名单封锁过期清除 — 业务逻辑梳理与有效期自定义计划

## 一、摘要（Summary）

梳理系统“黑名单封锁过期清除”的完整链路，并将“封禁有效期（block\_time）”从当前的硬编码 `30d` 落地为**可配置项**：后端注册配置 + 前端系统设置页可改默认值 + 数据源管理 auto-block 弹窗每次可指定时长（仅限定时长 d/h/m，不支持永久）。

核心结论：过期清除的**机制本身已可用且稳健**（定时清理、MAC 归一化、同 MAC 多防火墙防误解封、解封失败重试、解封后合规重算均已实现）；本次主要工作是把“有效期”从硬编码收敛为统一可配置，消除四处离散的 `30d`/内联解析逻辑，并修复一个让配置永远无法生效的读取 bug。

***

## 二、现状分析（Current State Analysis）

### 2.1 有效期写入路径（产生 expires\_at 的地方）

| 位置                                | 文件                                                                 | block\_time 来源                        | 现状             |
| --------------------------------- | ------------------------------------------------------------------ | ------------------------------------- | -------------- |
| 手动触发 auto-block                   | `compliance_service.py::auto_block_non_compliant` (L384, L542-552) | 请求参数 `request.block_time`（默认 `"30d"`） | 已支持传参，但前端写死    |
| 调度器 retry-block                   | `main.py` (L372-465)                                               | `service._get_block_time()`           | 受 bug 影响恒为 30d |
| 合规自动封锁 `_apply_compliance_result` | `compliance_service.py` (L1877-1909)                               | `self._get_block_time()`              | 受 bug 影响恒为 30d |
| 防火墙对账补建条目                         | `firewall_reconciliation_service.py` (L360-375)                    | 硬编码 `timedelta(days=30)`              | 硬编码            |
| CLI 造数                            | `cli.py` (L993)                                                    | 随机 7-30 天                             | 非生产，不改         |

### 2.2 有效期解析（\_parse\_block\_time）

* 顶层函数 `terminal_service.py::_parse_block_time` (L96-109)：正则 `^(\d+)([dhm])$`，支持天/时/分，非法回退 30 天。

* 另外三处**内联重复**了同一解析逻辑（`compliance_service.py` L542-552、L1878 附近、`main.py` L373 附近），行为一致但重复。

* `expires_at IS NULL` 语义为“永久封禁”，但 `_parse_block_time` 无“永久”入口（本次经确认**不需要**单独支持永久，仅限定时长）。

### 2.3 过期判定与清除执行（cleanup\_expired\_blacklist）

* 判定条件：`expires_at < now AND auto_unblocked == False`（`terminal_service.py::cleanup_expired_blacklist` L1866-2021）。

* 触发方式：`main.py::cleanup_expired_blacklist` 后台任务，间隔取 `scheduler_firewall_query_interval`（config 默认 300s；L107 兜底参数写 3600 但以 config 为准）。

* 执行逻辑（已实现且稳健）：

  1. 批量加载受影响 Terminals（按 `mac_address_normalized`，1 次查询）。
  2. 批量判定同 MAC 是否存在其它“活跃封锁条目”（`active_block_macs`），避免多防火墙场景误解封。
  3. 预解析每个 firewall\_tag 的 SangforService 实例（避免 N+1）。
  4. 逐条处理：同行仍有活跃条目 → 仅标记 `unblocked_at/by`；否则恢复终端 `status→unblocked`、`compliance_status→unknown`、`firewall_tag→None`，再调 Sangfor `unblock_ip`。
  5. 解封失败（防火墙禁用/缺失/API 错误）→ **不标记解封**，将 `expires_at` 延后 30 分钟重试，保证 DB 与防火墙一致。
  6. 提交后触发 `recalculate_all_compliance()`，让不合规终端尽快重新入封。

* 可用性保障：Redis 分布式锁、任务暂停控制、异常隔离、防火墙解封失败重试。

### 2.4 有效期自定义的现状问题（本次要解决的）

1. **配置项缺失**：`DEFAULT_CONFIGS`（`config_service.py` L68-232）中没有 `block_time`，前端系统设置页也无入口。
2. **读取 bug**：`compliance_service.py::_get_block_time` (L2241) 调用 `config_service.get("block_time", "30d")`，但 `ConfigService.get()` 签名仅接受 `key`（`config_service.py` L294），传两个参数会抛 `TypeError`，被 `except` 吞掉后恒返回 `"30d"` —— 配置即使加上也永远读不到。
3. **前端硬编码**：`ComplianceBaselinesTab.tsx` L340 `block_time: '30d'` 写死，弹窗无法指定时长。
4. **对账硬编码**：`firewall_reconciliation_service.py` L366 `timedelta(days=30)` 未跟随系统配置。

## 三、提议变更（Proposed Changes）

### 后端

#### 1. `backend/app/services/config_service.py` — 注册 block\_time 配置项

* **what**：在 `DEFAULT_CONFIGS` 的 compliance 分组（L144 `compliance_confirm_threshold` 之后）新增：

  ```python
  {"key": "block_time", "value": "30d", "category": "compliance",
   "value_type": "string",
   "description": "Default blacklist block duration (e.g. 1h/6h/12h/1d/3d/7d/15d/30d)"},
  ```

* **why**：使 block\_time 成为可被 `set()` 写入、`get()` 读取、并被启动时 `seed_defaults()`（`main.py` L711）自动补种的正规配置项。

* **how**：仅新增一条字典；`seed_defaults` 幂等，重启即补种，无需迁移。

#### 2. `backend/app/config_service.py` — get\_all\_grouped 暴露 block\_time

* **what**：`get_all_grouped()` 的 `ComplianceConfigResponse(...)`（L529-531）增加：

  ```python
  compliance=ComplianceConfigResponse(
      compliance_confirm_threshold=_val("compliance_confirm_threshold", 2),
      block_time=_val("block_time", "30d"),
  ),
  ```

* **why**：`/settings/` 返回的分组结果需包含 block\_time，前端系统设置页与弹窗才能读取默认值。

#### 3. `backend/app/schemas/system_config.py` — 响应模型加字段

* **what**：`ComplianceConfigResponse`（L143-145）增加 `block_time: str`。

* **why**：与第 2 步一致，保证 Pydantic 响应模型含该字段。

#### 4. `backend/app/services/compliance_service.py` — 修复 \_get\_block\_time 读取 bug

* **what**：`_get_block_time()`（L2233-2243）把 `return await config_service.get("block_time", "30d")` 改为 `return await config_service.get("block_time") or "30d"`。

* **why**：`ConfigService.get()` 只接受 `key`，原写法抛 `TypeError` 被静默吞掉，配置永远不生效。修复后才会真正返回 DB/Redis 中的 block\_time。

* **how**：最小改动一行；保留 try/except 兜底。

#### 5. `backend/app/services/firewall_reconciliation_service.py` — 去硬编码 30d

* **what**：补建 Blacklist 处（L360-375）的 `expires_at=datetime.now(UTC) + timedelta(days=30)` 改为读取系统 block\_time 并解析：

  ```python
  # 在循环外（或首次补建前）读取一次：
  from app.services.config_service import ConfigService
  from app.services.terminal_service import _parse_block_time
  block_delta = _parse_block_time(await ConfigService(self.db).get("block_time") or "30d")
  # 循环内使用：
  expires_at=datetime.now(UTC) + block_delta,
  ```

* **why**：让对账补建的兜底条目也跟随系统默认封禁时长，消除最后一处硬编码。

* **how**：`_parse_block_time` 为 `terminal_service` 模块级函数，`firewall_reconciliation_service` 与 `terminal_service` 无相互 import，单向导入安全（无循环依赖）。仅此一处读取 + 复用现成解析函数，不新增内联解析。

* **注意**：该条目对应“防火墙实际已封禁”的场景，Sangfor 封禁本身为永久；此处仅维持既有“跟随系统 block\_time”语义的一致性，不做额外业务变更。

### 前端

#### 6. `frontend/src/hooks/useTerminalData.ts` — 类型补充 + 预设常量

* **what**：

  1. `ComplianceConfig` 接口（L382-384）增加 `block_time: string;`。
  2. 新增导出预设常量：

     ```ts
     export const BLOCK_TIME_PRESETS = ['1h', '6h', '12h', '1d', '3d', '7d', '15d', '30d'];
     ```

* **why**：类型对齐后端新字段；预设常量供设置页与弹窗两处复用，保证取值合法。

#### 7. `frontend/src/pages/GeneralSettings.tsx` — 设置页暴露封禁时长

* **what**：

  1. `SECTION_FIELDS.compliance`（L50）由 `['compliance_confirm_threshold']` 改为 `['compliance_confirm_threshold', 'block_time']`。
  2. `Field` 渲染器对 `entry.key === 'block_time'` 增加 `<select>` 特判（参照现有 `log_level` 特判，L155-162），选项为 `BLOCK_TIME_PRESETS`，当前值若不在预设中则补一个 `value` 选项，`onChange` 直接回传选中字符串。

* **why**：把 block\_time 作为“合规”配置项暴露给管理员，且用下拉避免非法输入（`value_type` 为 string 无格式校验，后端 `_parse_block_time` 对非法值仅回退 30d，会让用户误以为保存成功）。

* **how**：`handleSave('compliance')` 已有逻辑会把它随其它项一起 `PUT /settings/update`，无需额外改动。

#### 8. `frontend/src/components/datasources/ComplianceBaselinesTab.tsx` — auto-block 弹窗每次可指定时长

* **what**：

  1. 引入 `useSettings`、`BLOCK_TIME_PRESETS`；新增状态 `const [autoBlockTime, setAutoBlockTime] = useState('30d')`。
  2. `handleAutoBlockClick`（L329-332）打开弹窗时，用系统配置初始化：`setAutoBlockTime(configs?.compliance?.block_time || '30d')`。
  3. Auto Block 确认弹窗（L432-444）在警告文案下新增一个“封禁时长”`<select>`（绑 `autoBlockTime`，选项 `BLOCK_TIME_PRESETS`，缺省补当前值）。
  4. `handleAutoBlockConfirm`（L338-342）把 `block_time: '30d'` 改为 `block_time: autoBlockTime`。

* **why**：消除前端硬编码，让每次手动 auto-block 可临时指定时长，默认回落到系统配置的 block\_time。

* **注意**：组件顶部需从 `useTerminalData` 一并 import `useSettings`、`BLOCK_TIME_PRESETS`（当前已 import `useComplianceBaselines, useDataSources` 等）。

#### 9. i18n（轻量）

* **what**：弹窗 label 复用现有 `t('blacklist.blockDuration')`（zh/en/ja 均已有，值为“封禁时长/Block Duration/ブロック期間”）。设置页 `Field` 的 label 沿用 `entry.key`，desc 沿用后端 `description`（英文）；如需中文 desc，可在 `FIELD_DESC_I18N_KEYS`（L116-122）新增 `'block_time': 'generalSettings.block_timeDesc'` 并在三个 locale 补该 key（可选，不阻塞主功能）。

* **why**：保持文案一致性，避免新增过多 key；中文 desc 为可选体验增强。

## 四、假设与决策（Assumptions & Decisions）

1. **有效期仅限定时长（d/h/m）**：经确认**不增加“永久封禁”选项**，`expires_at IS NULL` 的永久语义保持现状、不暴露入口。
2. **预设取值**：统一为 `1h / 6h / 12h / 1d / 3d / 7d / 15d / 30d`（与 `_parse_block_time` 支持的单位匹配），默认 `30d`。
3. **不重构既有解析逻辑**：三处内联解析（`compliance_service` 两处、`main` 一处）功能正确，本次仅修复 `_get_block_time` 读取 bug、复用 `terminal_service._parse_block_time` 消除 reconciliation 的硬编码，不做大范围统一重构（遵守“严格控制修改边界”）。
4. **无需数据库迁移**：本改动只涉及 config 值（SystemConfig 表）与业务读取，`Blacklist.expires_at` 字段已存在；新配置项由启动时 `seed_defaults()` 幂等补种。
5. **配置即时生效**：`set()` 会失效 Redis 缓存（`_invalidate_cache`），保存后下次 `_get_block_time` 即读到新值；已在运行的后台任务在下一轮循环读取新值。
6. **auto-block 弹窗默认值来源**：优先系统配置 `compliance.block_time`，缺失时回退 `'30d'`，不再硬编码。

## 五、验证步骤（Verification）

1. **重建部署**：`./manage.sh update`（本地代码重建 + 重启，无 git pull）。
2. **配置补种校验**：确认 seed 后 config 表含 block\_time：

   * `docker exec tam_backend python -m ...` 或调用 `GET /settings/list?category=compliance`，应返回含 `block_time`、`value="30d"`、`value_type="string"` 的条目。
3. **分组接口校验**：`GET /settings/` 返回的 `compliance` 对象应含 `block_time: "30d"`。
4. **设置页保存校验**：前端系统设置页“合规”分组出现 block\_time 下拉，修改为如 `7d` 并保存成功；再次 `GET /settings/` 返回 `7d`。
5. **读取 bug 修复指纹校验**：

   * 容器内 `grep -n 'or "30d"'` 命中 `compliance_service.py::_get_block_time`；确认已无 `get("block_time", "30d")` 双参调用。
6. **auto-block 弹窗校验**：数据源管理页选择 ARP 数据源 → 点“自动封禁”，弹窗出现“封禁时长”下拉，默认值等于系统配置；改为其它时长确认后，请求体 `block_time` 与所选一致（可临时在浏览器 Network 或后端日志确认）。
7. **端到端一致性校验**：手动触发一次 auto-block（自定义短时长如 `1h`），确认新建 Blacklist 的 `expires_at ≈ now + 1h`；等待/触发清理后确认过期条目被正确解封、终端状态复位并触发合规重算。
