### 2.1 合规状态判定流程（`recalculate_all_compliance` / `check_compliance`）

每个终端在每个周期执行一次完整判定，优先级如下：

```
1. 白名单匹配 (_match_whitelist_in_memory)
   └─ IP 模式匹配 && MAC 精确匹配 → bypass（权威，立即生效，无确认计数）
2. 作用域判断 (_check_terminal_in_arp_scope)
   └─ 命中 ip_cidr / ip_range / mac_prefix_arp → use_ip_only=True（只查 IP）
3. IPGuard 基线匹配
   ├─ use_ip_only=True → _match_ipguard_ip_only_in_memory（仅 IP 相等）
   └─ use_ip_only=False → _match_ipguard_in_memory（IP+MAC 精确 或 IP+MAC前缀）
4. 结果：IPGuard 命中 → compliant；否则 → non_compliant
```

关键依据点（[recalculate_all_compliance](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2060-L2130)）：

- **非白名单路径受反振荡「确认计数」约束**：`_get_confirm_threshold()` 默认 `2`（系统配置 `compliance_confirm_threshold`）。
  - `non_compliant → compliant`：需连续 `compliant_confirm_count >= 阈值`（默认 2 个周期约 10 分钟）才真正切换，代码日志关键字 `CONFIRMED upgrade non_compliant → compliant`。
  - `compliant → non_compliant`：需连续 `non_compliant_confirm_count >= 阈值`。
  - `bypass → non_compliant`：特殊保护，需连续 6 次白名单丢失才降级。
- **IP 变更宽限期**：`ip_changed_at` 在近 10 分钟内且非 bypass → 不降级（等待 IPGuard 数据跟上）。

### 2.2 non_compliant → compliant 的可能触发原因

`compliant` 必须同时满足「非白名单」且「IPGuard 匹配」。导致 `ig_match` 由假变真的原因只能是以下之一：

1. **IPGuard 基线数据更新**（IP/MAC 新出现在 IPGuard 库中）。
2. **终端 IP 或 MAC 变化（DHCP）**：新 IP/MAC 落入 IPGuard 基线。
3. **作用域条件变更**：新增 `ip_cidr/ip_range/mac_prefix_arp` 使该终端转为 `use_ip_only`，只匹配 IP 即可。

> 判定具体属于哪一种，需查该终端 `updated_at`、`ip_changed_at`、当时的审计日志，以及 IPGuard 缓存 / 作用域配置。

### 2.3 自动解封流程与「待重试解封」的产生

「待重试解封」口径（[get_blacklist_stats](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1638-L1648)）：

```
pending_retry_unblock =
    活跃黑名单条目 (auto_unblocked=False AND unblocked_at IS NULL AND 未过期)
    JOIN 终端
    WHERE 终端.compliance_status IN ('compliant','bypass')
```

即：**终端的 `compliance_status` 已经是 compliant/bypass，但仍存在未解封的活跃黑名单条目**。这只会发生在一个场景——**解封动作执行失败**：

- 在 [auto_unblock_compliant](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L848-L899) 中，只有「所有防火墙均解封成功（`all_success=True`）」才把条目标记 `auto_unblocked=True`；任一防火墙失败则条目保持活跃。
- 在 [_apply_compliance_result](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L1630-L1631、L1785-L1786) 中，**先无条件把 `terminal.compliance_status = new_compliance` 写入**，再尝试解封；若所有防火墙解封均失败（`successful_fw_tags` 为空），则 `status` 仍为 `blocked`、条目未标记 `auto_unblocked` → 形成「compliant + 活跃黑名单」= 待重试解封。

**关键澄清**：黑名单条目的 `reason` 字段（如「IP 和 MAC 都不合规」）是**创建封锁时写入的历史原因**，不随终端当前合规状态更新。因此「看到 reason 是 IP/MAC 都不合规」与「终端当前已 compliant/bypass」并不矛盾。

## 四、假设与关键判断点

- **假设 1（10.8.12.184）**：最可能是「IPGuard 基线刷新 / DHCP 换 IP / 作用域新增 IP-only」三者之一，使 `ig_match` 由假变真，并经 `compliant_confirm_count ≥ 2` 连续确认后切换 `non_compliant → compliant`。以 `audit_logs` 的 `old/new_compliance` 与 IPGuard 缓存内容做最终定论。
- **假设 2（10.8.18.44）**：黑名单 `reason='IP 和 MAC 都不合规'` 是**历史封锁原因**；终端当前 `compliance_status` 已变为 compliant/bypass（依据同假设 1），随后自动解封在防火墙侧失败（`last_operation_status='failed'`），导致「compliant + 活跃黑名单」= `pending_retry_unblock`。以 `3.2` 的 `last_operation_status/error` + `3.1` 的 `compliance_status` 做最终定论。
- **假设 3**：若某 IP 存在**多条黑名单**（多防火墙 / 多时间段），需逐条核对，避免只用最新一条下结论。
