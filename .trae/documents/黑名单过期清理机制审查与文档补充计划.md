## 一、审查结论（直接回答）

**是。** 黑名单条目在到达 `expires_at`（封禁到期时间）后，系统会由后台定时任务**自动**向深信服（Sangfor）防火墙发起解封请求，清除过期条目，并恢复终端与数据库状态。

核心链路：

```
main.py 启动后台任务 cleanup_expired_blacklist()
   └─ 周期扫描 Blacklist
        ├─ 判定：expires_at < now AND auto_unblocked == False
        └─ 对每条过期条目调用 sangfor_service.unblock_ip()  → 向防火墙发 DELETE 请求
             ├─ 成功 → 软删除 DB 条目 + 恢复终端状态 + 触发合规重算
             └─ 失败 → 不标记解封，expires_at 延后 30 分钟重试
```

该机制**已实现且稳健**，无需新增功能。

## 二、现状分析（Current State Analysis）

### 2.1 数据模型

`backend/app/models/blacklist.py`：

- `expires_at`（DateTime timezone，nullable，index）— 封禁到期时间。
- `auto_unblocked`（Boolean，default False）— 是否已被自动解封。
- `unblocked_at` / `unblocked_by` — 软删除标记（解封时间/操作人）。
- `firewall_tag` / `mac_address_normalized` — 用于定位防火墙与终端。

### 2.2 触发与调度（backend/app/main.py）

- 后台任务 `cleanup_expired_blacklist()`（L104-124）：`while True` 循环，周期取：
  - `scheduler_firewall_query_interval`（经 `_get_scheduler_interval` 读取并 clamp 到 30–86400s，兜底 3600s）。
- 启动点：lifespan 中 `asyncio.create_task(cleanup_expired_blacklist())`（L785）。
- 并发保护：
  - 暂停开关：`_is_task_paused("firewall_query")`（Redis 键 `scheduler:ctrl:firewall_query`）。
  - 分布式锁：`_acquire_task_lock("firewall_query")`（`SET NX EX`，多实例防重）。
- 异常隔离：整段 try/except，出错仅记 `[source=scheduler]` 日志，不影响下一轮。

### 2.3 清理执行逻辑（backend/app/services/terminal_service.py L1885-2051）

`cleanup_expired_blacklist()` 关键实现要点：

1. **查询**：`select(Blacklist).where(expires_at < now, auto_unblocked == False)`；为空返回 0。
2. **批量预加载（防 N+1）**：
   - 终端：按 `mac_address_normalized` 一次加载，键为 **`(mac_address_normalized, ip_address)`** 复合对（`terminal_by_pair`，L1903-1910）。
   - 活跃封锁：一次查询仍在生效的 `(mac_address_normalized, ip_address)` 对（`active_block_pairs`，L1914-1928）。筛选条件 `unblocked_at IS NULL AND auto_unblocked == False AND (expires_at >= now OR expires_at IS NULL)`。
   - 防火墙实例：按 `firewall_tag` 预解析并缓存 `SangforService`（`sangfor_cache`，L1930-1935）。
3. **逐条处理**（L1942-2022）：
   - `pair_key = (mac_norm, entry.ip_address)`。
   - **同 `(MAC, IP)` 仍有其它活跃封锁** → 仅软删除本条（`unblocked_at/by`），**不对防火墙解封**。
   - **是该 `(MAC, IP)` 最后一条活跃封锁** → 向防火墙发送解封请求 `svc.unblock_ip([{"srcIP": entry.ip_address}])`（L1971）。
     - 成功（`code == 0`）→ 软删除本条 + 若终端 `status == "blocked"` 则恢复 `status=unblocked`、`compliance_status=unknown`、`firewall_tag=None`、`block_state=None`（L1998-2015）。
     - 失败：`code != 0` / 防火墙禁用或缺失 / 异常 → **不标记解封**，将 `expires_at` 延后 `now + 30min` 供下一轮重试，并记录失败 IP（L2016-2022）。
4. **收尾**：`count > 0` 时写审计日志并 `commit`，随后触发 `recalculate_all_compliance()` 闭环（L2030-2045）。

### 2.4 防火墙解封实现（backend/app/services/sangfor_service.py L376-437）

`unblock_ip()` 对每个 IP：

1. `_find_blacklist_entry(ip)` 查防火墙黑名单（whiteblacklist search API）。
2. 仅删除 TAM 管理条目（`is_tam_managed_entry`，description 带 `TAM:` 前缀）。
3. 调用 `DELETE .../whiteblacklist/{ip}` 删除。
4. 返回 `code = 0 if len(unblocked) > 0 else 1`。

## 三、审查发现（Findings）

### 发现 1（文档与代码不一致，需修正文档）

业务流程文档 §6.3 描述的活跃封锁判定粒度仍为 **MAC 级**，与当前代码 **`(MAC, IP)` 复合对** 粒度不一致（v3.20 终端唯一标识改为 (IP, MAC) 复合键后，清理逻辑同步更新，但文档未同步）：

| 文档措辞（stale） | 当前代码（实际） |
|---|---|
| `active_block_macs`（MAC-only） | `active_block_pairs`（键为 `(mac_address_normalized, ip_address)`） |
| `processed_macs` 去重 | `processed_pairs` 去重 |
| 「同 MAC 仍有其它活跃封锁」 | 「同 `(MAC, IP)` 仍有其它活跃封锁」 |

### 发现 2（已知边界，仅需文档说明，不改代码）

`unblock_ip()` 对「防火墙中已不存在该 IP」或「条目非 TAM 管理」的情形，结果计入 `skipped`（未计入 `unblocked`），最终返回 `code=1`。`cleanup_expired_blacklist` 将 `code != 0` 判为失败 → 保留 DB 条目并每 30 分钟重试。

这是**保守兜底**（宁可 DB 条目残留，也不冒「防火墙已清但 DB 误标解封」的不一致风险），并非缺陷；但当前文档未说明，宜补充为「已知边界」。
