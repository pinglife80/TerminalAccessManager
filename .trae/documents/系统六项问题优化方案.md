## 二、逐项分析

### 问题 1：备份列表无折叠/分页

**现状**
[Backup.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Backup.tsx#L545-L592) 中主备份列表直接 `backups.map(...)` 全量渲染，[白名单备份列表](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Backup.tsx#L616-L657) 同样全量渲染，均无分页。备份文件会随保留天数持续累积，列表过长时页面卡顿且可读性差。

**根因**
`Backup.tsx` 未引入项目已存在的可复用分页组件 [Pagination.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/components/Pagination.tsx)。该组件已被 Blacklist、ComplianceBaselines、OperationSource 等页面广泛使用。

**方案**
- 后端 `list_backups` / `list_whitelist_backups` 返回全量列表，采用**前端客户端分页**即可，无需改后端。
- 在 `Backup.tsx` 增加分页状态（`backupPage`、`backupPageSize`，默认 10），对 `backups` 和 `whitelistBackups` 分别 `slice` 后渲染，并各自挂载 `<Pagination>`。
- 参照 [Blacklist.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx#L513-L522) 的底部 `variant="bottom"` 用法。

### 问题 2：数据源中文后端日志 unicode 乱码

**现状**
[logging_config.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/core/logging_config.py#L79-L107) 的 `_json_format` 中 `json.dumps(log_data)` 未设置 `ensure_ascii`，Python 默认 `ensure_ascii=True`，会把中文转义为 `\uXXXX`。生产环境 JSON 日志（stdout 与 `/var/log/tam/app.log`）中所有中文（如数据源同步的提示、防火墙连接错误信息）都变成 unicode 转义序列。

**根因**
`json.dumps` 默认对非 ASCII 字符做转义，需显式 `ensure_ascii=False`。

**方案**
- 修改 [logging_config.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/core/logging_config.py#L104)：
  ```python
  result = json.dumps(log_data, ensure_ascii=False) + "\n"
  ```
- 该改动同时作用于 stdout 与文件 handler（二者均复用 `_json_format`），一处即修复全部日志输出。无需改动其它日志调用点。

### 问题 3：角色仅小写开头、创建后无法编辑（编辑提示“已存在”）

**现状**
1. [Roles.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Roles.tsx#L441-L450) 的 `RoleFormModal.handleSave` 使用正则 `/^[a-z][a-z0-9_]*$/` 强制名称以小写字母开头，导致无法创建 `SecurityAdmin`、`Audit_Pro` 等带大写/连字符的角色名。
2. 前端编辑时 `handleSave` 始终把当前角色名 `name` 一并提交（未改名也提交原名）。后端 [roles.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/roles.py#L185-L191) `update_role` 的名称唯一性校验**未排除自身**：
   ```python
   existing_role = await db.execute(select(Role).where(Role.name == data.name))
   if existing_role.scalar_one_or_none():
       raise HTTPException(status_code=400, detail=f"Role '{data.name}' already exists")
   ```
   当未改名时，`data.name == role.name`，该查询会命中**当前角色自身**，于是即使只修改描述或权限也会误报"Role 'xxx' already exists"（即用户看到的"提示已存在"）。

**根因**
- 前端正则限制过严（仅小写开头）。
- 后端 `update_role` 名称唯一性校验缺少 `Role.id != role_id`，编辑时把自己判为重复。

**方案**
- **后端（修复"提示已存在"）**——修改 [roles.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/roles.py#L189) 的唯一性校验，排除自身：
  ```python
  existing_role = await db.execute(
      select(Role).where(Role.name == data.name, Role.id != role_id)
  )
  if existing_role.scalar_one_or_none():
      raise HTTPException(status_code=400, detail=f"Role '{data.name}' already exists")
  ```
  这样未改名（只改描述/权限）与真正的改名都可用，仅当改名为**其它已存在角色名**时才报重复。
- **前端（放开大小写/连字符）**——放宽 [Roles.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Roles.tsx#L447) 的正则为允许大小写字母、数字、下划线、连字符，且仅要求以字母开头：
  ```typescript
  if (!/^[a-zA-Z][a-zA-Z0-9_-]*$/.test(name.trim())) {
  ```
- 同步更新提示文案（`roles.invalidRoleNameFormat`）为"以字母开头，仅包含字母、数字、下划线、连字符"。

> 说明：内置角色（admin/operator/auditor/viewer）名称在后端 `update_role` 中禁止重命名，属既有既定设计，不在本次改动范围。

### 问题 4：会话超时提醒无手动关闭、超时不自动注销

**现状**
[useTokenExpiration.ts](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/hooks/useTokenExpiration.ts#L42-L51) 用 `sonner` 的 `toast.warning(..., { duration: 10000 })` 展示提醒，10 秒后自动消失，无「继续会话/关闭」等手动操作入口；[App.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/App.tsx#L201) 的 `<Toaster position="top-right" richColors />` 也未配置持久关闭按钮。

**注销链路核对**
- 登录成功时 `useAuthStore.login` 已写入 `token_expires_at`：[auth.ts](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/store/auth.ts#L41-L49)。
- token 到期前 60 秒走 `handleRefresh` 自动续期（滑动会话），refresh 失败才 `handleExpired` 注销；空闲 30 分钟走 `handleIdleTimeout`。
- `handleExpired`/`handleIdleTimeout` 里 `logout()` 只清 session + 置 `isAuthenticated=false`，跳转依赖 `setTimeout(() => { window.location.href = '/login' }, 500)`。

**根因**
1. 提醒用一次性 toast，无可手动关闭/续期的交互，10 秒即消失。
2. 注销与跳转逻辑分散在 `handleExpired` / `handleIdleTimeout` 两处，且依赖原始 `window.location.href` 硬编码 `/login`，一旦被浏览器/路由拦截或 `token_expires_at` 缺失（如旧会话、非本 hook 写入）时，仅清 store 而不跳转，页面停留在原处 → 表现为"超时后不会自动注销"。

**方案**
- 用一个带倒计时、可手动关闭的**对话框**替换 toast 提醒（新建独立组件或内联于 hook 返回值），提供「继续会话（重置空闲计时）」「立即退出登录」两个按钮 + 右上角关闭按钮；倒计时结束时自动调用注销。
- 抽出一个统一的 `performLogout()`：清空 `access_token`/`refresh_token`/`token_expires_at`、调用 `useAuthStore.getState().logout()`、并 `window.location.replace('/login')` 单一路径跳转，`handleExpired` 与 `handleIdleTimeout` 复用，消除重复与硬编码跳转依赖。
- hook 返回提醒触发状态，由 [App.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/App.tsx) 或 `Layout` 渲染对话框，保证关闭/续期操作可用。
- 当 `token_expires_at` 缺失时应视为已过期，直接走注销而非静默 `return`，修复"不注销"的兜底逻辑。

### 问题 5：删除数据源/绑定/合规基线时待清理统计有误

**现状与根因（按类型）**

数据源删除预览在 [data_source_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/data_source_service.py#L105-L251) 的 `preview_delete_data_source`：

1. **防火墙（sangfor）删除**——终端/封堵终端计数错误：
   - 预览用 `Terminal.source_tag == tag` 统计（[L127](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/data_source_service.py#L127)），但防火墙相关的终端是由 `Terminal.firewall_tag` 关联（见真实删除逻辑 [L338-L342](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/data_source_service.py#L338-L342) 用 `Terminal.firewall_tag.contains(tag)`）。
   - 结果：删除防火墙时 `terminals`/`blocked_terminals` 恒为 0，与实际"解封 N 个终端"不符。

2. **ARP 源删除**——黑名单统计口径偏差：
   - 预览用 `Blacklist.source_tag == tag OR Blacklist.firewall_tag == tag`（[L134-L136](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/data_source_service.py#L134-L136)）。对 ARP 源应仅按 `source_tag == tag` 统计（`firewall_tag` 只对防火墙有意义）；虽大多数场景 `firewall_tag == tag` 不命中，但口径与实际删除逻辑不一致，存在误报风险。

3. **绑定关系删除**（`preview_delete_binding` [L431-L485](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/data_source_service.py#L431-L485)）：
   - `blocked_count = len(set(bl.ip_address for bl in bl_entries))` 未排除 `ip_address` 为 NULL 的补建/对账条目，导致"待解封终端数"把 NULL-IP 记录也计入，与实际解封动作（仅对有 IP 的黑名单条目执行 `unblock_ip`）不符。
   - `affected.terminals` 恒为 0 但 `blocked_terminals` 被赋值，语义不清。

4. **合规基线删除**（[compliance_baselines.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/compliance_baselines.py#L131-L184) `preview_delete_baseline`）：
   - 预览直接统计全库 `compliance_status IN ("compliant","non_compliant")` 的所有终端（[L158-L163](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/compliance_baselines.py#L158-L163)），未按该基线的 `tag` 过滤，导致删除任一基线时显示的是**全系统**合规/不合规终端数，严重偏大。
   - 真实删除动作（[L187-L218](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/compliance_baselines.py#L187-L218)）只删除基线行 + 清理 `ipguard:{tag}` 缓存 + 触发全量重算，不删除任何终端。

**方案（使预览统计与真实清理动作一一对齐）**

- **防火墙（sangfor）分支**：
  - `terminal_count` / `blocked_count` 改为按 `Terminal.firewall_tag.contains(tag)` 统计（`blocked_count` 取其中 `status == "blocked"` 的数量）。
  - `bl_count` 改为 `Blacklist.firewall_tag == tag`。
  - `bind_count` 保持 `firewall_tag == tag`（`arp_source_tag` 对防火墙不命中，可保留 OR 亦可收紧，建议收紧为 `firewall_tag == tag`）。
- **ARP 分支**：
  - `bl_count` 改为 `Blacklist.source_tag == tag`。
  - `bind_count` 改为 `DataSourceBinding.arp_source_tag == tag`。
  - `terminal_count` / `blocked_count` 保持 `source_tag == tag` 不变。
- **绑定删除**：
  - `blocked_count` 仅统计非空 `ip_address` 的去重个数：`set(bl.ip_address for bl in bl_entries if bl.ip_address)`。
  - 将 `affected.blocked_terminals` 用于该值（语义 = 待解封终端数），`affected.terminals` 仍为 0（绑定删除不解绑终端记录本身）。
- **合规基线删除**：
  - 将 `compliant_terminals` 改为"该基线 tag 关联的合规终端数"，不再全库统计。实现：复用 [compliance_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py) 中的 `_load_all_ipguard_cache` / `_match_ipguard_in_memory`，按当前基线 `tag` 的缓存对 `compliance_status == "compliant"` 的终端做匹配，得到"删除后将被重新评估/失去合规态"的终端数。
  - `affected` 其余字段（terminals/blacklist_entries/bindings）保持 0，与真实删除动作一致。
  - `warnings` 文案由"覆盖 N 个合规终端 / 关联 N 个不合规终端"改为体现"删除后 N 个合规终端将被重新评估，不合规终端可能被自动封堵"。

### 问题 6：暗黑模式输入/下拉字体不可视、黑名单背景不同步

**现状**
[index.css](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/index.css) 定义了 `.dark` 的 CSS 变量，但：

1. 未声明 `color-scheme`。浏览器原生表单控件（`<select>` 的下拉选项、日期/时间控件、自动填充底色、滚动条等）在暗黑模式下仍按浅色渲染，与深色文本叠加形成"无对比/不可视"。
   - `darkMode: 'class'` 见 [tailwind.config.js](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/tailwind.config.js#L3)。

2. [Blacklist.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx) 的行悬停/自动封堵高亮使用了硬编码浅色类，暗黑模式下不生效、与卡片主题不同步：
   - 行悬停 `hover:bg-blue-50/30`（[L404](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx#L404)、[L406](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx#L406)）
   - 自动封堵高亮 `bg-orange-50/30`（[L406](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx#L406)）
   - 统计卡片 `text-green-600` / `text-yellow-600` / `text-blue-600` 等纯色在深色卡片上对比不足。

**方案**
- 在 [index.css](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/index.css) `@layer base` 增加：
  ```css
  :root { color-scheme: light; }
  .dark { color-scheme: dark; }
  ```
  并在 base 层显式让表单控件使用前景色（保证输入/下拉文字可读）：
  ```css
  input, select, textarea { @apply text-foreground; }
  ```
  > 说明：Tailwind preflight 已将表单控件 `color: inherit`，但显式声明可避免个别组件 `text-muted-foreground` 被覆盖造成歧义；若担心覆盖，可改为仅针对 `.dark` 下未指定前景色的原生控件兜底。`color-scheme` 是解决原生下拉选项不可视的关键。
- 将 [Blacklist.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx) 的硬编码浅色类改为语义 token + dark 变体：
  - `hover:bg-blue-50/30` → `hover:bg-muted/40`
  - `bg-orange-50/30` → `bg-orange-500/10 dark:bg-orange-500/15`
  - 统计卡片纯色文字（`text-green-600` 等）在暗黑下补充 `dark:text-green-400`、`dark:text-yellow-400`、`dark:text-blue-400` 等变体，或改用既有语义类。
- 保持黑名单表格 `thead bg-background` / `tbody bg-card` 与 Roles、ComplianceBaselines 等页面一致。

## 四、假设与决策

1. 备份列表数据量属于前端可承载范围，采用客户端分页即可，不引入后端分页参数（与既有 `list_backups` 全量返回保持一致）。
2. 角色名放宽到 `[a-zA-Z][a-zA-Z0-9_-]*`，允许大小写与连字符；内置角色仍维持"不可重命名"的既有约束。
3. 会话提示采用对话框而非继续用 toast，以提供明确的"手动关闭/续期/注销"入口，符合用户对非侵入式、可操作提醒的偏好。
4. 问题 5 的修复原则是"预览统计 = 真实清理动作"，不改变实际删除行为，仅修正展示口径，避免引入额外业务逻辑。
5. 问题 6 只修黑名单页的硬编码浅色，其它页面同类硬编码色暂不扩散处理（遵循最小改动边界）。
6. 所有改动均在本地 `manage.sh update` 重建 + 验证后生效；不改变 VERSION（本次为缺陷修复，如需发布另走发布计划）。

## 五、验证步骤

1. **备份分页**：进入备份管理，生成 >10 个备份后确认列表分页切换、每页数量选择、末页/首页按钮正常；白名单列表同样分页。
2. **日志中文**：触发一次数据源同步/连接测试，检查 `docker logs tam_backend` 及 `/var/log/tam/app.log` 中中文不再出现 `\uXXXX`，直接显示中文。
3. **角色**：创建名为 `SecurityAdmin`、`Audit_Pro` 的角色成功；对已创建的自定义角色改名含大写/连字符成功；内置角色仍不可重命名、描述/权限可改。
4. **会话超时**：缩短本地 token/空闲时长验证——提醒对话框出现且可手动关闭/续期；不操作至超时后页面自动跳转 `/login`。
5. **删除统计**：分别为 ARP、防火墙、绑定、合规基线执行"删除预览"，核对显示的待解封终端数、黑名单条数、绑定数、合规终端数与实际清理动作一致（重点：删除防火墙时不再显示 0 终端；删除任一基线时不再显示全系统终端数）。
6. **暗黑模式**：切换暗黑主题，确认全局输入框/下拉框文字可见（含下拉展开项）、黑名单行悬停与自动封堵高亮与主题同步。
7. **回归**：`manage.sh update` 重建后，执行后端测试套件确认无回归（尤其 data_source_service、compliance_baselines 相关用例）。
