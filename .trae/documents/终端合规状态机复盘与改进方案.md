# 终端合规状态机复盘与改进方案

> 文档版本：v3.17.0  更新日期：2026-08-26

## 一、核心思想要求（复盘基准）

1. **检测准确性、稳定性**：合规判定本身必须准确、稳定，不得因缓存/时序抖动产生误判。
2. **谨慎降级到 non\_compliant（核心边界）**：从其它状态变为 `non_compliant` 会触发封锁、影响终端正常使用，因此该转变必须**谨慎、明确**，不能轻易降级，避免误封锁与频繁封锁。
3. **迅速升级到 compliant/bypass**：从 `non_compliant` 变为 `compliant` 要**先正确、后迅速**。
4. **白名单迅速生效**：手动添加白名单（MAC-only / IP-only / MAC+IP）后应立即将该终端变为白名单（bypass）状态。

## 二、当前实现现状分析（客观）

### 2.1 状态机定义

`Terminal.compliance_status` 四种状态：`unknown`（初始）/ `bypass`（白名单）/ `compliant`（IPGuard 匹配）/ `non_compliant`（都不匹配）。

`Terminal.status` 仅表示防火墙封堵状态：`blocked` / `unblocked`。

### 2.2 关键流转路径

| 路径            | 触发点                                                                                                                                                                                                  | 是否经过确认阈值                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| A. 首次发现       | [arp\_collector\_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/arp_collector_service.py#L398-L409) `batch_check_compliance` → `_apply_compliance_result` | ❌ 无（立即 unknown→non\_compliant 并封锁）                                            |
| B. 首次发现（调度兜底） | [main.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py#L294-L344) 同上直接 `_apply_compliance_result`                                                                    | ❌ 无                                                                           |
| C. 周期全量复核     | [compliance\_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L1959-L2223) `recalculate_all_compliance`                               | ✅ 有 `compliance_confirm_threshold`（默认 2）+ IP 宽限期 + 白名单 miss 阈值 + IPGuard 陈旧保护 |
| D. 自动封锁兜底     | `auto_block_non_compliant` + retry-block（main.py）                                                                                                                                                    | 部分                                                                            |

| F. 手动白名单      | `add_to_whitelist` → `apply_manual_whitelist_for_terminal`                                                                                                                                           | ✅ 绕过冷却期立即生效                                                                   |

### 2.3 已符合思想要求的良好设计（应保留）

* **周期复核的确认阈值**：`compliance_confirm_threshold`（默认 2，可配置），要求连续 N 次检测才降级/升级，防抖正确。

* **白名单权威性**：`wl_result` 命中直接 `bypass`，无需确认、不参与防抖（符合"白名单迅速生效"）。

* **手动白名单立即生效**：`apply_manual_whitelist_for_terminal` 绕过冷却期，立即置 `bypass` 并解封（符合"迅速"）。

* **IPGuard 数据完全不可用时中止重算**（`ipguard_total == 0`），避免整网误判 non\_compliant。

* **IPGuard 缓存陈旧保护**：`ipguard_stale_threshold_minutes`（默认 12，可配置），陈旧时阻断 non\_compliant 降级方向。

* **IP 变更宽限期**（`ip_changed_at`）：DHCP 换 IP 后 10 分钟内容忍，避免 IPGuard 基线未跟上导致误封锁。

* **白名单 miss 阈值**（6 次连续 miss 才降级 bypass→non\_compliant），防止白名单缓存瞬时失效误判。

* **冷却期防抖**：自动解封/自动封锁/降级前均有 10 分钟冷却，防止解封-封锁震荡。

* **动作-状态一致性**：`auto_unblock_compliant` 与 `_apply_compliance_result` 解封时同步设 `compliance_status`（whitelist→bypass、IPGuard→compliant），避免中间态。

* **封锁失败回滚**：`_apply_compliance_result` 全防火墙封锁失败时回滚 `compliance_status`。

* **分布式锁**：`recalculate_all_compliance` 用 Redis 锁防并发重算。

* **retry-block 白名单权威预检**：main.py retry-block 前先 `_match_whitelist_in_memory` 自愈。

### 4.5 P2-1 首次发现路径纳入确认阈值

* 方案（推荐，符合思想要求 2 的"谨慎降级"）：首次发现路径不再直接 `unknown→non_compliant` 并封锁，而是让其进入与周期复核一致的确认逻辑。

  * 具体实现：在 `arp_collector_service.process_arp_entries` 与 `main.py scheduled_compliance_check` 两处，将 `unknown` 终端的判定结果先仅**累加确认计数**而非直接 `_apply_compliance_result` 封锁；仅当 `non_compliant_confirm_count >= compliance_confirm_threshold` 时才置 non\_compliant 并封锁。或更简单：两处首次发现路径的 `new_compliance` 为 `non_compliant` 时，改为调用统一的"带阈值的降级"帮助方法，业务上复用 `recalculate_all_compliance` 的 `_apply_compliance_result` 前置确认逻辑。

  * 兜底：保留周期 `recalculate_all_compliance`（每循环运行）作为最终一致性收敛，首次路径从"立即封锁"退化为"标记候选+由周期复核确认+封锁"，代价是首次封锁延迟一个确认周期（默认约 300s），换取误封锁风险显著下降。

* 备选（若希望保持首次即时封锁）：保持现状，但在文档中明确"首次发现即封锁"为有意识的产品取舍，仅补充 IPGuard 缓存陈旧保护到首次路径（当前首次路径未做 `ipguard_cache_stale` 检查）。

* 决策说明见第五节。

  ```python
  key = mac_norm_key if mac_norm_key else (entry.ip_address or "")
  ```

  终端查找也相应处理：仅当 `mac_norm_key` 非空时按 `mac_address_normalized` 查终端；为空的 NULL-MAC 条目按 `ip_address` 查终端（`select(Terminal).where(Terminal.ip_address == current_ip)`）。

* 理由：与 `_blacklist_terminal_key()` / 对账服务 / 统计口径保持一致，使 NULL-MAC 对账条目也能被正确自动解封。

### 4.7 P2-3 MAC+IP 白名单立即生效前校验 IP

* 文件：`backend/app/services/terminal_service.py` `add_to_whitelist`

* 改动：在 `wl_match_type == "both"` 分支，调用 `apply_manual_whitelist_for_terminal` 前，先校验 `ip_pattern` 是否命中 `terminal.ip_address`（复用 `IPAddressParser` / `_match_whitelist_in_memory` 的 matches 逻辑）；只有命中才立即置 bypass，否则不做立即置 bypass（交给周期复核自然判定）。

* 理由：避免 MAC+IP 白名单因 IP 不匹配而瞬时误置 bypass，保证"白名单迅速生效"的同时不破坏正确性。

### 4.8 P3 清理项

* 删除 `arp_collector_service._auto_block_task` 死代码。

* 删除 `main.py` retry-block 中未使用的 `cooldown_cutoff_retry` 变量。

* 在 `auto_block_non_compliant` 封锁前增加白名单权威预检（`_match_whitelist_in_memory`），命中则自愈为 bypass 并跳过封锁（对齐 retry-block 已有逻辑）。

## 五、假设与决策

1. **首次发现确认阈值**（P2-1）是唯一有行为取舍的点，最终采用**方案 A（纳入阈值）**：因为思想要求 2 明确要求"不能轻易从其它状态变为 non\_compliant"，且周期复核已证明阈值机制可靠，首次路径当前"0 阈值立即封锁"是明显的不对称缺陷。若使用者希望保留首次即时封锁，应在评审时明确否决本项。

3. P0/P1/P2-2/P2-3/P3 均无行为歧义，直接按方案实施。
4. 改动范围为后端 `compliance_service.py`、`terminal_service.py`、`arp_collector_service.py`、`main.py`、`config_service.py`、`schemas/system_config.py`，以及前端 `useTerminalData.ts`、`GeneralSettings.tsx`、i18n（`zh.ts`/`en.ts`/`ja.ts`）；新增配置项由 `seed_defaults` 幂等补齐，**不涉及数据库表结构迁移**。
