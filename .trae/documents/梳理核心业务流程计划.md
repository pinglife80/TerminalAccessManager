## 3. 拟议变更（Proposed Changes）

### 3.1 主文件：`docs/business-workflow.md`

**做什么**：将其从 v3.12.0 更新为 v3.13.0，作为本次梳理的最终落点。

**为什么**：这是唯一承载"核心业务流程"主题的既有文档，且已存在分层结构（采集/判定/封锁/解封/黑名单/状态机/参数/事件），就地校正比新建文档更符合项目"文档版本随发布一致"的约束。

**怎么做**（逐项）：

1. **文档头**：`> 文档版本：v3.12.0  更新日期：2026-08-20` 改为 `> 文档版本：v3.13.0  更新日期：2026-08-24`。

2. **§3.5 三层防震荡**：改写「auto\_unblock 解耦」小节 → 改为「action-state 一致性」小节，说明 `auto_unblock_compliant` 解封时同步写 compliance\_status（白名单→bypass / IPGuard→compliant），并清零确认计数，避免中间态引发统计口径错乱与被 retry-block 重封。

3. **新增 §（防火墙对账流程）**，内容包含：

   * 触发：`firewall_reconciliation()` 后台任务，**硬编码 300s**；也可通过 `POST /system/firewall-reconciliation` 手动触发。

   * 权威原则：**防火墙实际状态是封锁状态的唯一事实源**；对账只改 `status`，不改 `compliance_status`。

   * 节点与判断标准：

     * **补建 DB 缺失（最高优先级）**：防火墙有封锁 IP 但 DB 无活跃黑名单 → `_create_db_entries_for_firewall`；白名单(bypass)终端被误封时**跳过建条目**并告警，交由合规重算安全解封。

     * **DB 有但防火墙缺 → 重新封锁**：`_reblock_on_firewall`。

     * **0-IP 保护**：防火墙返回 0 条但 DB 有活跃条目时，做单点探测（`_find_blacklist_entry`）区分"列表接口异常"与"外部清空"，二者都**保守跳过**防止数据丢失。

     * **孤立 blocked 自愈**：`_repair_stale_terminal_status` 把 `status=blocked` 但无活跃黑名单背书的终端重置为 `unblocked`（仅改 status，不动 compliance\_status）。

   * 结果缓存：最新对账结果写入 Redis `reconcile:latest`（TTL 1h），供黑名单页 stats 展示。

4. **新增 §（后台调度任务周期汇总表）**，内容见下方 §3.2（决策层直接复用的权威表）。

5. **§4.5 封堵失败重试**：更新为当前 `scheduled_compliance_check` 的**四段式**真实流程，补充「retry-block 白名单权威自愈预检」（whitelist 命中→置 bypass，单独提交，不回滚）。

6. **§6 黑名单管理**：补充对账创建的黑名单条目（`NULL-MAC` 回退 IP 匹配、`source_tag="reconciliation"`）说明。

7. **§8 关键参数**：补充 `compliance_confirm_threshold`（默认 2，范围 1-10）、`block_time`（默认 30d）、对账周期(300s 硬编码)、冷却期/宽限期(10min 硬编码)、缓存 TTL（ipguard 900s / whitelist 300s / scope 300s）等真实值与来源（配置 vs 硬编码）。
