# 三问题根因诊断与优化解决方案报告

## 一、概述

本报告针对三个已定位根因的问题，分别给出：根因回顾、可选方案对比、推荐方案、实施方案、影响评估与验证方法。

| 1 | 交换机 ARP 存在某 IP，但终端管理页永不出现（如 `10.8.14.32` 与 `10.8.14.100` 共用 MAC） | 终端以 **MAC 为唯一键**（`uq_terminal_mac` 单列唯一），同 MAC 多 IP 时第二个 IP 被折叠丢弃 | **高（架构级）** |

## 二、问题1：终端唯一键 MAC → MAC+IP 改造方案

### 2.1 根因回顾（已确认）

`10.8.14.32` 与 `10.8.14.100` 在交换机 ARP 表中映射到同一个 MAC。而系统在以下三处将 "MAC" 当作终端唯一身份：

- [arp_collector_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/arp_collector_service.py#L279-L306)：`seen_macs` 按 MAC 批内去重，`scalar_one_or_none()` 按 MAC upsert。
- [terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L50)：`UniqueConstraint('mac_address_normalized', name='uq_terminal_mac')`。
- 下游多处 `Blacklist.mac_address_normalized == terminal.mac_address_normalized` 按 MAC 关联。

关键共识（已核实）：**防火墙封禁、黑名单唯一索引早已是 IP 维度**（`svc.block_ip(ip)`、`idx_blacklist_unique_active` 为 `(ip_address, firewall_tag)`）。真正还锁在 "MAC 单列唯一" 的是 terminals 表本身及其派生的查询/统计/关联逻辑。

### 2.2 方案选项对比

| 方案 | 思路 | 优点 | 缺点/风险 | 结论 |
|---|---|---|---|---|
| **A. MAC+IP 复合唯一键（整体改造）** | 唯一键改为 `(ip_address, mac_address_normalized)`，同步修正所有 MAC-only 查询/关联 | 与下游 IP 维度完全对齐，真正支持"同 MAC 多 IP"独立展示与独立封堵 | 改动面大（约 8 个模块、18+ 处），需全量回归 | **推荐（长期正确方案）** |
| B. 多 IP 旁表（`terminal_ips`） | Terminal 仍按 MAC 唯一，ARP 采集把 (mac,ip) 写入旁表，前端展示多 IP | 合规/封堵核心逻辑改动小，保留 DHCP 稳定身份 | 无法满足"同 MAC 不同 IP 不共享封堵状态"的诉求；需新增表+前端+同步逻辑，复杂度不低 | 备选（若想降低核心逻辑风险） |
| C. 仅前端 IP 维度修正 | 不改后端唯一键，仅把 `Terminals.tsx` 的 `blackMacSet` 命中改为 IP 维度 | 改动最小、风险最低 | 不解决"IP 永不落库"的根本问题，10.8.14.32 仍看不到 | 可作临时缓解，非根治 |

### 2.3 推荐方案

**采用方案 A（MAC+IP 复合唯一键）**，并按里程碑分阶段实施、逐段回归。理由：系统下游已是 IP 维度，方案 A 使全链路身份模型收敛为 "一个 (IP, MAC) 终端"，与"防火墙按 IP 封堵"的事实一致，也直接呼应 [Terminals.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Terminals.tsx#L218-L220) 中"同 MAC 不同 IP 不应共享封堵状态"的既有意图。

### 2.5 影响评估

| 影响维度 | 说明 |
|---|---|
| 数据模型 | 唯一键变更，需一次迁移；`ip_address` 语义从"可变属性"变为"身份组成"，`mac_address_normalized` 建议 NOT NULL |
| 采集 | 多 IP 正确落库、合规结果不串扰；需验证 DHCP 换 IP 场景（旧 (mac,旧IP) 变 offline，新 (mac,新IP) 新建） |
| 合规/封堵 | 封堵本就 IP 维度，无方向性变化；但解封/冷却/活跃黑名单查询需全部加 IP，**漏改任一处会产生"错 IP 解封/再封"** |
| 统计 | "设备数 vs 行数"语义需重新定义并全链路对齐，否则卡片与列表对不上 |
| 对账/清理 | 需按 (mac,ip) 关联，否则补建/状态修复/过期清理会错乱 |
| 前端 | 仅黑名单命中 + 文案，改动小 |
| 回归风险 | **高**：涉及 8 模块，建议逐里程碑编译 + 单元/集成测试 + 指定 4 场景手工回归 |

### 2.6 风险与缓解

- **漏改下游查询导致"错 IP 解封/封"**：用统一 helper（如 `_terminal_identity()` 返回 (mac,ip) 判等表达式）收敛所有关联点，避免散落裸 SQL。
- **DHCP 换 IP 产生多终端/重复计数**：上线前明确统计语义；确保离线检测按 (mac,ip) 正确处理旧记录。
- **迁移大表锁/耗时**：`uq_terminal_mac` 唯一约束变更建议在低峰执行，先备份；迁移脚本保留完整的 upgrade/downgrade 与去重逻辑。
- **回滚**：保留 `040` 的 downgrade；回滚后需重新去重（因 MAC+IP 可能产生了同 MAC 多行）。

## 三、问题2：通知消息补全方案

### 3.1 根因回顾

通知链路：`emit_*()` → `NotificationService.emit()` → Redis 队列 → `NotificationWorkers` → `_get_subscribed_channels()`（按 `channel.events` 精确匹配）→ 规则/模板 → 渠道 `send()`。

缺失原因（四层叠加）：
1. 渠道 `events` 订阅列表未勾选其它事件（worker 直接 drop）。
2. 7 个事件只有 emitter 定义、无调用点（`system.error/warning/alert`、`security.email_verified`、`alert.auto_block_triggered/auto_unblock_triggered/policy_violation`）。
3. 业务动作无 emit：封锁失败、重试封锁、白名单增删、手动重试解封。
4. 事件字典缺 whitelist/blacklist 变更类型；无默认订阅 seed。

### 3.2 方案选项与推荐

| 方案 | 内容 | 结论 |
|---|---|---|
| A. 补 emit + 新增事件类型 + 默认订阅 seed（完整） | 后述 8-10 项 | **推荐** |
| B. 仅补 emit（不新增类型/不改订阅） | 只能补已有事件码的调用点，白名单变更仍无事件类型；且不改订阅则存量渠道仍收不到 | 不完整 |
| C. 仅默认订阅 | 解决"有事件无订阅"，但不解决"无调用点/无业务事件" | 不完整 |

### 3.3 实施方案

#### 后端（前端零改动，事件清单动态来自 `GET /notifications/events`）

1. **事件字典** [event_types.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/notification_channels/event_types.py)：
   - `EventType` 新增 `WHITELIST_CHANGED = "admin.whitelist_changed"`（如需黑名单变更再增 `admin.blacklist_changed`）。
   - `EVENT_METADATA` 新增对应 `<name/description/severity/category>`。
   - 新增常量 `DEFAULT_SUBSCRIBED_EVENTS = [e.value for e in EventType]`。
2. **发射器** [event_emitter.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/event_emitter.py)：新增 `emit_whitelist_changed(action, identifier, operator, details=None)`；其余复用已有 `emit_terminal_blocked/unblocked`、`emit_system_error/warning`。
3. **业务调用点补全**：
   - [compliance_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L662-L664) `auto_block_non_compliant` 失败分支：`emit_system_error(error_type="auto_block_failed", ...)`。
   - 同文件 `_apply_compliance_result` 成功分支（L2064-2112 末尾）`emit_terminal_blocked(...)`；全失败分支（L2113-2133）`emit_system_error/warning(...)`。
   - [terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py) `add_to_whitelist`（L801 前）与 `delete_from_whitelist`（L912 前）：`emit_whitelist_changed("add"/"remove", ...)`。
   - 同文件 `retry_unblock` 成功分支（L1785-1801）`emit_terminal_unblocked(..., username)`；失败分支可选 `emit_system_error`。
4. **默认订阅 seed**：
   - [notification_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/notification_service.py#L149-L180) `create_channel`：`events` 为空时回填 `DEFAULT_SUBSCRIBED_EVENTS`。
   - 新增幂等方法 `ensure_default_subscriptions()`，为存量 enabled 渠道补齐缺失事件并 commit。
   - [main.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py#L766-L780) lifespan 初始化中，`initialize_channels()` 之后调用 `ensure_default_subscriptions()`。

#### 前端

- 事件清单/勾选/筛选/规则模板均动态来自 `GET /notifications/events`，**自动出现，零改动**。
- 可选 UX：[Notifications.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Notifications.tsx#L139) 将新建渠道 `events` 默认值由 `[]` 改为全选（后端已兜底则可不动）。

### 3.4 影响评估

- **风险低**：`emit_event` 是 fire-and-forget，错误只记日志不抛异常，新增 emit 不会影响业务主流程。
- **模板缺失**：无 `NotificationTemplate` 时渠道走 `base.format_message`（用 metadata 渲染），不会"发不出"，仅内容通用。
- **订阅补齐是配置变更**：`ensure_default_subscriptions` 会写回渠道 `events`，需幂等且只增不减，避免覆盖管理员有意取消的订阅（建议按"缺失项并入"而非"重置为全量"）。

## 四、问题3：双清单重叠方案

### 4.1 根因回顾

- `success_blocked` = active 黑名单行数（[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1631-L1635)）。
- `pending_retry_unblock` = active 黑名单 + `Terminal.compliance_status IN ('compliant','bypass')`（L1640-1650），是前者的**子集**。
- 对账 [firewall_reconciliation_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/firewall_reconciliation_service.py#L371-L386) 补建 active 黑名单（reason=对账文案），且只写 `Terminal.status='blocked'`、不改 `compliance_status`；若终端已合规，则同时落入两清单，直到自动解封成功写回 `auto_unblocked=True` 才消失。

### 4.2 方案选项对比与推荐

| 方案 | 内容 | 对防震荡影响 | 结论 |
|---|---|---|---|
| **A. UI 口径说明** | 两张卡片加 tooltip/说明：pending 是 success 的子集；对账补建的已合规终端在解封前会同时计入 | 无 | **推荐（低风险，先做）** |
| B. 对账补建时对已合规终端"跳过/立即解封" | 直接跳过会令防火墙实际封锁与 DB 事实源脱节、并诱发 reconcile 与 status 修复之间 5min 抖动；直接解封会绕过 10min 冷却 | 直接冲突 | 不推荐"直接跳过/直接解封" |
| B'. 对账补建后"排队/触发受冷却保护的 `auto_unblock_compliant`" | 保持冷却，合规终端仍坐满窗口才解封 | 不破坏，但窗口不减 | 可选（与 A 组合） |
| C. 统计口径改为互斥 | `success_blocked` 排除已 compliant/bypass 条目，使两口径互斥 | 需三处（stats/list/count）+ 前端默认列表全对齐，否则新的卡片/列表不一致 | 谨慎，仅在明确要"互斥数字"时用 |

**推荐组合：A（UI 口径说明）+ B'（对账补建已合规终端时排队一次受冷却保护的解封，可选）**。不改变统计口径（避免引入新的不一致），以最低风险消除困惑，并在不破坏防震荡的前提下让中间态更早收敛。
