## 0. 结论先行（探查实锤）

一句话：**当前「根治方案」（新增 `Terminal.block_state` + 统计口径对齐）确实解决了「口径混乱」与「中间态无分类」两个层面，但并没有消除用户看到的三个现象的数值本身**——因为线上真实数据表明，根因不在「标记/口径」，而在「防火墙封锁真实失败」与「防火墙-DB 对账真实未收敛」。

通过对线上运行环境（已部署 v3.17.3，迁移 037 已应用）的真实数据抽样，得到如下硬证据：

| 指标 | 线上实测值 | 含义 |
|---|---|---|
| `non_compliant + blocked` | 109 | 非合规已封锁终端 |
| `non_compliant + unblocked + block_failed` | 96 | 封锁失败待重试 |
| `non_compliant + unblocked + block_state=NULL` | 54 | **尚未被调度器分类的中间态** |
| `non_compliant + unblocked + no_firewall` | 0 | 不可封锁（本环境无此类） |
| 活跃黑名单条目数 / 去重 IP 数 | 259 / **258** | 全部挂在唯一防火墙 `af`（sangfor, enabled） |
| 防火墙实际封锁 IP 数（`reconcile:latest`） | **200** | 单防火墙，无跨防火墙去重因素 |
| 防火墙-DB 差值 | **58**（258 − 200） | DB 认为已封锁但防火墙实际没有 |

三条用户问题的业务判定（详见第 3 节）：

1. **「非合规且封锁」与「防火墙实际封锁」对不上** → 口径混乱已修复（Dashboard `blocked` 与黑名单 `success_blocked` 已统一为「去重活跃黑名单 IP」=258），但 **258 vs 200 的 58 个真实差值仍存在**，属对账未收敛，非口径问题。
2. **大量非合规未封锁** → 分类已完成（96 block_failed / 54 NULL / 0 no_firewall），但 **150 个非合规未封锁仍在**，其中 96 是真实封锁失败。
3. **大量 Block Pending Retry** → no_firewall 已从 retry 中剔除（本环境正好为 0），但 **block_failed=96 仍持续构成 retry 积压**，直到封锁真正成功。

**总判断：该方案是「必要但不充分」的根治。它把「看不懂的对不上」变成了「看得懂的对不上 + 看得懂的积压」，但尚未关闭数字本身。** 下文给出可复现的验证步骤与验收标准，用来正式确认这一点，并定位剩余根因。

## 2. 验证目标与总体方法

**目标**：用可复现的只读数据 + 可控触发，回答「三点问题是否真被解决」，并区分「已解决」「解决口径但未解决数值」「未解决」三个层次。

**方法**：
1. 数据口径一致性验证（SQL 不变量比对，判定"该相等的相等"）
2. 中间态收敛验证（触发调度器，观察 NULL → classified）
3. 封锁失败根因验证（定位 96 个 block_failed 的失败原因）
4. 防火墙-DB 对账验证（定位 58 个差值来源）
5. 前端展示一致性验证（三页口径 + 卡片标注）
6. 自动化测试覆盖缺口确认

---

## 3. 三点问题逐一验证方案

### 3.1 问题 1：「非合规且封锁」vs「防火墙实际封锁」对不上

**已解决部分（口径）**：
- Dashboard `blocked` 与黑名单 `success_blocked` 现已同源，都应是 258。验证不变量 I1。

**未解决部分（真实差值）**：
- `firewall_ip_count`=200 与 `success_blocked`=258 差 58，且本环境仅一个防火墙 `af`，**排除多防火墙去重因素**。这是真实的「DB 有、防火墙无」不一致。
- 验证不变量 I4，并在第 3.4 节定位 58 个差值的本质（re-block 失败？NULL-MAC 补建？对账缓存陈旧？）。

**验收标准**：
- ✅ 口径一致：`get_stats().blocked == get_blacklist_stats().success_blocked`
- ⚠️ 数值一致：需确认 58 差值能否被对账关闭；若对账后仍差距 >0，判定问题 1 **未根治**（仅诊断清晰化）

### 3.2 问题 2：大量非合规未封锁

**已解决部分（分类）**：150 = 96(block_failed) + 54(NULL) + 0(no_firewall)，每类已可区分。

**未解决部分（数值）**：150 仍存在，其中 96 是封锁失败、54 是未收敛。

**验收标准**：
- ✅ 分类完备：不变量 I2 成立（`non_compliant_unblocked == pending_retry_block + unblockable_non_compliant`）
- ❌ 收敛：不变量 I3 要求 `block_state IS NULL` 的中间态 == 0；当前 54 > 0，**未通过**
- ⚠️ 数值下降：只有定位并修复 96 个封锁失败根因后，非合规未封锁数才会实质下降

### 3.3 问题 3：大量 Block Pending Retry

**已解决部分**：`no_firewall` 不再计入 retry（本环境 0，恰好不构成永久积压）。若未来出现无绑定防火墙数据源，将正确归入「不可封锁非合规」，不会再假重试。

**未解决部分**：`pending_retry_block` = NULL(54) + block_failed(96) = 150，其中 96 是持续失败的封锁。

**验收标准**：
- ✅ retry 口径正确：retry 只含 `NULL / block_failed`，不含 `no_firewall`
- ⚠️ retry 清零：需定位 96 个 block_failed 的失败根因；否则「Block Pending Retry」会持续=96+（新失败还会继续累积）

## 4. 关键验证步骤（可执行）

### 步骤 A：口径一致性 SQL 校验（只读）

```sql
-- I1: dashboard.blocked 与黑名单 success_blocked 同源（期望相等）
SELECT COUNT(DISTINCT ip_address) FROM blacklist
WHERE auto_unblocked = false AND unblocked_at IS NULL
  AND (expires_at IS NULL OR expires_at >= now());
```

```sql
-- I2 左侧: non_compliant + unblocked（enabled ARP 源）
SELECT COUNT(*) FROM terminals t
JOIN data_sources ds ON ds.tag = t.source_tag
WHERE ds.type IN ('arp_ssh','arp_api') AND ds.enabled
  AND t.compliance_status='non_compliant' AND t.status='unblocked';
-- I2 右侧拆分: 按 block_state
SELECT COALESCE(block_state,'NULL') AS bs, COUNT(*) FROM terminals t
JOIN data_sources ds ON ds.tag = t.source_tag
WHERE ds.type IN ('arp_ssh','arp_api') AND ds.enabled
  AND t.compliance_status='non_compliant' AND t.status='unblocked'
GROUP BY 1;
```

```sql
-- I3: 未分类中间态应清零（当前 54，为失败点）
SELECT COUNT(*) FROM terminals t
JOIN data_sources ds ON ds.tag = t.source_tag
WHERE ds.type IN ('arp_ssh','arp_api') AND ds.enabled
  AND t.compliance_status='non_compliant' AND t.status='unblocked'
  AND t.block_state IS NULL;
```

### 步骤 B：中间态收敛触发验证

1. 记录触发前 `block_state=NULL` 计数（目标快照 54）。
2. 手动触发一次合规检查（`manage.sh scheduler trigger`，或调用合规检查端点），等待一个调度周期（默认 300s）完成。
3. 复跑步骤 A 的 I3 查询，观察 54 → 0 or（no_firewall / block_failed / blocked）。
4. 若仍残留 NULL，说明 retry-block 对 `yp` 源未完整执行或中途异常回滚，需查 `tam_backend` 日志中 `[source=scheduler]` 相关 ERROR。

### 步骤 C：封锁失败根因定位（96 block_failed）

1. 取样本：`SELECT ip_address, mac_address FROM terminals WHERE compliance_status='non_compliant' AND status='unblocked' AND block_state='block_failed' LIMIT 10;`
2. 查后端日志中对应 IP 的 `Retry block failed` / `Failed to block` 记录，提取 `sangfor_service.block_ip` 返回的 code/message。
3. 判定失败类别：防火墙 API 返回业务错误（IP 已存在/参数错/权限）vs 网络异常 vs 服务未解析（`sangfor_services[fw_tag]=None`）。
4. 若属「IP 已存在」这类软失败（幂等误判为失败），则需修复 `_block_on_firewall` 的判定逻辑；若属真实连接失败，则需修复防火墙连接/凭据。

### 步骤 D：防火墙-DB 对账差值定位（58 gap）

1. 读 `reconcile:latest`（`redis-cli get reconcile:latest`），比对 `firewall_ip_count` / `db_entry_count` / `synced_at`。
2. 手动触发对账（`./manage.sh scheduler trigger` 或调用 reconciliation 端点），观察下一轮缓存中 `firewall_ip_count` 是否向 258 收敛。
3. 若不收敛，取 `missing_in_fw`（DB 有、防火墙无）样本，逐条调用 `sangfor.get_blocked_ips` 与单点 `_find_blacklist_entry` 探测，确认是「re-block 失败」还是「列表接口返回不完整」。
4. 重点排查 [firewall_reconciliation_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/firewall_reconciliation_service.py) 中 `_reblock_on_firewall` 是否**静默吞掉**单 IP 重封失败（当前该失败不写入 `firewall_errors`）。

### 步骤 E：前端三页一致性校验（只读）

1. Dashboard → `blocked` 数值 == 黑名单页 `success_blocked` 数值（应相等，均为去重活跃黑名单 IP）。
2. 终端页「非合规已封锁」== `stats.non_compliant`（=109）；「非合规待封锁」== `stats.non_compliant_unblocked`（=150）。
3. 黑名单页「Block Pending Retry（pending_retry_block）」+「不可封锁非合规」== 终端页「非合规待封锁」（=150）。
4. 黑名单页「防火墙实际封锁」== `firewall_ip_count`（=200，且带「未跨防火墙去重」提示）。

### 步骤 F：测试覆盖缺口确认

- 当前 [backend/tests](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/tests) 中 **无任何** 对 `get_stats` 新字段、`get_blacklist_stats` 拆分口径、`block_state` 状态机的单测（grep 确认 0 命中）。
- 1473 个通过测试不覆盖本次改动 → 需补充：`get_stats` / `get_blacklist_stats` 口径单测、`block_state` 三值收敛单测、与三类中间态分类单测。

## 5. 不变量定义（验收基准）

| 编号 | 不变量 | 期望 | 当前实测 |
|---|---|---|---|
| I1 | `blocked == success_blocked` | 相等 | 待复核（应=258） |
| I2 | `non_compliant_unblocked == pending_retry_block + unblockable_non_compliant` | 恒等 | =150，✓ |
| I3 | `count(non_compliant+unblocked+block_state IS NULL) == 0` | 为 0 | =54，❌ |
| I4 | 对账收敛后 `firewall_ip_count ≈ success_blocked`（单防火墙下应相等） | 相等 | 200 vs 258，❌ |
| I5 | `non_compliant(blocked) <= success_blocked` | 成立 | 109 ≤ 258，✓ |

## 6. 探查中发现的残余缺口（供决策）

1. **`firewall_ip_count` 依赖缓存**：读 `reconcile:latest`（TTL 1h）。缓存失效或从未对账时显示 0，前端需结合 `synced_at` 提示「上次对账时间」，避免新困惑。
2. **对账 re-block 失败不透明**：`_reblock_on_firewall` 的单 IP 重封失败未计入 `firewall_errors`，导致「对账成功但数据库/防火墙仍不一致」被静默掩盖——这是 58 gap 的重要嫌疑点。
3. **Dashboard 未展示非合规指标**：仅 `total/whitelisted/blocked`，问题 1/2 的非合规维度只在终端页与黑名单页可见。
4. **测试覆盖为 0**：本次改动无单测锁定，回归风险高。

## 7. 结论与后续建议

**验证结论（预判）**：本方案**修复了「口径混乱」与「中间态无分类」**（I1/I2/I5 预期成立），但 **I3（54 个 NULL 未收敛）与 I4（58 个防火墙-DB 差值）预期不成立**，即**问题 2、3 的数值未实质下降，问题 1 的真实差值仍存在**。

**建议后续（需另行授权实施，不在本次验证范围）**：
1. 修复 `_block_on_firewall` 对「IP 已存在」等软失败的误判（根因级解决 96 block_failed）。
2. 让对账 `_reblock_on_firewall` 失败可观测（写入 `firewall_errors`），追平 58 gap。
3. 调度器 retry-block 增加「兜底 sweep」，确保 `block_state=NULL` 的中间态必被分类（关闭 I3）。
4. 补单测锁定口径与状态机。
