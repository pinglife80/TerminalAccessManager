# 终端/黑名单统计分类与数据口径说明

> 本文件只做**解释说明**，不包含任何代码改动。目标是回答三个问题：
> 1. 终端管理为什么把「非合规」拆成「非合规已封锁 / 非合规待封锁」两张卡？
> 2. 黑名单管理为什么出现「成功封锁 / 防火墙实际封锁 / 不可封锁非合规」等分类？
> 3. 为什么这些数字看起来「对不上」？以及「仅启用 ARP 源」是什么意思。

---

## 一、背景：这些分类是怎么一步步长出来的

系统核心是一条**异步管道**：

```
ARP 采集终端 → 合规检测 → 判定 non_compliant → 调度器调防火墙封堵 → 对账核对防火墙实际状态
```

这条管道天然存在时间差与失败场景，于是历史上反复出现「终端显示不合规、但防火墙其实没封上」「解封后又自动重封」「统计数字比实际封禁数还多」等问题。为了把每种**中间态/卡死态**都摆到台面上，就逐步加出了下面这些分类。它们不是凭空设计，而是逐个 bug 修复沉淀下来的（见项目记忆里的“action-state consistency 原则”、“中间态”、“retry-block / retry-unblock”等）。

关键前提：`Terminal` 上同时存在两个**相互独立**的字段——

- `status`：只表示**防火墙封锁状态**（`blocked` / `unblocked`），见 [terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L9-L15)。
- `compliance_status`：合规状态（`compliant` / `bypass` / `non_compliant` / `unknown`），见 [terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L35-L41)。

一旦这两个字段“不同步”（例如 `non_compliant` 但还没封上），就会出现“不合规却没封锁”的中间态，这是所有拆分统计的根源。

## 二、终端管理的统计（6 张卡）

前端卡片在 [Terminals.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Terminals.tsx#L727-L789)，数据来自后端 `get_stats`：[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L254-L338)。

| 卡片 | 后端字段 | 口径 |
|---|---|---|
| 总数 | `total` | 启用 ARP 源的终端数 |
| 正常 | `compliant` | `compliance_status='compliant'` |
| 绕过 | `bypass` | `compliance_status='bypass'` |
| **非合规已封锁** | `non_compliant` | `non_compliant` **且** `status='blocked'`，按 **distinct IP** 去重 |
| **非合规待封锁** | `non_compliant_unblocked` | `non_compliant` **且** `status='unblocked'`，按终端计数 |
| 待检查 | `unknown` | `compliance_status='unknown'` |

### 为什么要把「非合规」拆成两张卡？

因为「非合规」和「已封锁」是**两个动作**，中间隔着一次异步的防火墙调用：

1. 合规判定为 `non_compliant` 时，终端先进入 `non_compliant + unblocked`（**待封锁中间态**）。
2. 调度器 `retry-block` 调防火墙，成功后 `status` 才变成 `blocked`。

早期只统计一个笼统的「非合规」总数时，出现了「非合规数 > 已封禁数」的怪象——因为把“正在封/还没封/封不上”的都混在一起了，进而引发“自动解封→重封”的震荡。修复原则固化成了：**保持 `compliance_status='non_compliant'` ⇒ `status='blocked'` 这条不变量**（action-state consistency）。

于是把两者分开展示：

- 「非合规已封锁」：已经落地的、终态的那部分（`non_compliant + blocked`，按 distinct IP 去重，避免 DHCP 复用 IP 被重复计数）。
- 「非合规待封锁」：还在管道里、或卡住的那部分（`non_compliant + unblocked`）。

为了进一步解释“待封锁”里**为什么卡住**，又给 `Terminal` 加了 `block_state` 字段（[terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L41-L44)）：

- `None` → 正常。
- `no_firewall` → ARP 源没绑定防火墙，**永远封不了**。
- `block_failed` → 封过但失败了，**可被 retry 重封**。

见 [terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L42-L44) 的字段注释。

## 三、黑名单管理的统计（7 张卡）

前端卡片在 [Blacklist.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx#L169-L275)，数据来自后端 `get_blacklist_stats`：[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1626-L1755)。

| 卡片 | 后端字段 | 口径 |
|---|---|---|
| 成功封锁 | `success_blocked` | 活跃黑名单记录按 **distinct IP** 去重 |
| 防火墙实际封锁 | `firewall_ip_count` | 各防火墙上报封锁 IP 数之和，**跨防火墙不去重**（来自 `reconcile:latest` 缓存） |
| 封锁失败待重试 | `pending_retry_block` | `non_compliant + unblocked` 且 `block_state ∈ (None, block_failed)` |
| 不可封锁非合规 | `unblockable_non_compliant` | `non_compliant + unblocked` 且 `block_state='no_firewall'` |
| 成功解封 | `success_unblocked` | 已被解封的记录数 |
| 解封失败待重试 | `pending_retry_unblock` | 记录仍活跃、但终端已 compliant/bypass（解封失败待重试） |
| 防火墙异常 | `firewall_errors` | 最近一次对账失败的防火墙列表 |

### 为什么黑名单会出现「成功封锁 / 防火墙实际封锁 / 不可封锁非合规」？

因为黑名单页面本质是“**DB 对封堵的记录**”，而**真相在防火墙**。系统有专门的对账服务 `firewall_reconciliation_service`，周期性去每个防火墙拉取真实封锁 IP 列表，再和 DB 比对：

- 「成功封锁」= **DB 认为**还活跃封着的 IP 数（`success_blocked`）。
- 「防火墙实际封锁」= **防火墙实际上报**的封锁 IP 数（`firewall_ip_count`）。

这两者**天然不等**，原因包括：对账延迟、`block_failed`（DB 有记录但防火墙没真封上）、以及「补建条目」（防火墙有、DB 没有时，对账会补一条 `mac_address` 为 NULL 的黑名单记录，见 `_blacklist_terminal_join` 里对 NULL-MAC 回退到 IP 的处理：[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L36-L52)）。

而「不可封锁非合规」是把 `block_state='no_firewall'`（根本没绑定防火墙、永远封不了）单独拎出来，避免它混进「待重试」里让“可操作性”的数字失真。

所以黑名单这 7 张卡，等于把“封堵流水线”的每一环状态都拆开展示：**已封（DB）/已封（防火墙）→ 待封（可重试 / 不可封）→ 待解封 → 已解封 → 异常防火墙**。

## 四、为什么「数据对不上」

根因是这套系统里同时存在**三种口径**，且去重维度还不一致：

| 口径 | 出处 | 去重方式 |
|---|---|---|
| A. 终端 `status` | `Terminal.status` | 终端维度 / distinct IP（不统一） |
| B. 黑名单 DB 记录 | `Blacklist` 表 | distinct IP |
| C. 防火墙实际状态 | 对账缓存 `reconcile:latest` | 各防火墙求和、**不去重** |

再叠加几个边界情况，导致表面数字对不上：

1. **NULL-MAC 补建记录**：对账发现“防火墙有、DB 缺”时补的黑名单记录，`mac_address` 为 NULL。它在「Dashboard 已封禁 / 成功封锁」里按 IP 算进去了，但在终端表里**没有对应终端**，所以「非合规已封锁」（按终端 distinct IP）不含它。
2. **DHCP 换 IP**：同一终端换 IP 后，按 IP 去重会漏或重，部分地方改用“MAC 归一化、NULL 回退 IP”去重（`_blacklist_terminal_key`：[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L55-L58)），口径又不完全一致。
3. **跨防火墙不去重**：「防火墙实际封锁」是每个防火墙各自 IP 数相加（不跨防火墙去重，见中文提示 [zh.ts](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/i18n/locales/zh.ts#L470)），而「成功封锁 / blocked」是 DB distinct IP，两者从定义上就不是同一个数。
4. **同一批“待封锁”被拆到两个页面**：终端页「非合规待封锁」= `non_compliant + unblocked`（含 `no_firewall` + `block_failed`）；黑名单页把它拆成「封锁失败待重试」（None/block_failed）+「不可封锁非合规」（no_firewall）。即：
   `终端·非合规待封锁 = 黑名单·封锁失败待重试 + 黑名单·不可封锁非合规`，但分处两页、名字不同，看起来像“对不上”。

> 按照本次确认的口径基准：**以防火墙实际状态为准**（firewall actual state 是真相）。那么「数据对不上」的正确理解应当是：DB 侧数字只是“期望值/记录”，最终要通过对账收敛到 `firewall_ip_count`；当前对不上要么是**对账还没收敛**，要么是 `block_failed`/`no_firewall` 这类**永远无法收敛**的存量。

## 五、「仅启用 ARP 源 (Enabled ARP Only)」是什么意思

- 终端来源不止 ARP：还有 IPGuard、手动、白名单等；而“合规检测 + 自动封堵”这套逻辑**只针对 ARP 采集的终端**。
- 后端统一用 `_enabled_arp_source_tag_condition()` 限定口径：只统计 `source_tag` 属于**当前启用的、类型为 `arp_ssh`/`arp_api` 的数据源**的终端，见 [terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L61-L70)。
- Dashboard 统计、终端页统计卡片**默认就是这个口径**（只数启用的 ARP 源）。
- 而终端列表默认会显示**所有来源**的终端。为了不让「列表行数」和「统计卡片」对不上，前端加了个复选框「仅启用 ARP 源」（[Terminals.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Terminals.tsx#L622-L632)），勾选后把列表/筛选也切到“只看启用的 ARP 源”，对应后端 `arp_enabled_only` 参数（[schemas/terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/schemas/terminal.py#L50)、[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L486)）。

一句话：**“Enabled ARP Only”= 只统计/展示那些来源仍处于启用状态的 ARP 数据源的终端**，是让“统计卡片口径”与“列表口径”对齐的开关，不是某种合规状态。

## 六、结论

- 这些分类不是重复造轮子，而是把「异步封堵 + 对账」管道里的**中间态 / 卡死态 / DB 与防火墙差异**显式化了。
- 复杂度与「数据对不上」来自**三种口径并存**（终端 status / 黑名单 DB / 防火墙实际）再加上 **distinct IP、MAC 归一化、跨防火墙不去重**等去重差异。
- 若要收敛，方向应为：**统一以防火墙实际状态为唯一真相源**，DB 侧数字退化为“待对账差异”，并精简跨页重复的分类卡片。但这属于后续改造，本次按约定**不落地代码**。
