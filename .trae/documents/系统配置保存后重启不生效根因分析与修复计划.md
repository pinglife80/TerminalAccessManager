# 系统配置「保存后重启不生效」根因分析与修复计划

> 文档版本：v3.21.0  更新日期：2026-10-13

---

## 1. 摘要

系统配置存在**双数据源**：前端「系统设置」页保存写入数据库表 `system_config`，但**部分运行时消费代码直接读取环境变量 `.env`（Pydantic `settings`）而非数据库**，导致这些配置项保存后自始不生效——与是否重启服务**无关**。

已确认一个明确失效项：**「允许注册」`allow_registration`**（保存进 DB，但注册端点读 `.env`）。其余安全/合规/调度/告警/缓存配置经排查**均已正确读库**，无问题。

---

## 2. 配置存储与加载链路（现状）

保存链路（正确无误）：

- 前端 `GeneralSettings.tsx` 调 `PUT /api/v1/settings/update`
- → `backend/app/api/v1/endpoints/settings.py::update_configs`
- → `ConfigService.batch_update()` / `set()`（`backend/app/services/config_service.py`）
- → 写库 `system_config` 表 + 删除 Redis 缓存键 `sys_config:{key}`（立即热加载）

读取链路（热加载、库优先）：

- 业务代码用 `get_config_value(key, default)` 或 `ConfigService.get()`
- 顺序：Redis 缓存 → 数据库 → `.env` 回退（`config_service.py` 第 312-342、572-644 行）

启动链路：

- `main.py::lifespan` → `init_db()` → `ConfigService.seed_defaults()`
- `seed_defaults` **仅对不存在的 key 播种**（第 255-277 行），不会覆盖已存在 key

> 结论：保存落库是持久的（PostgreSQL），不因重启丢失；`seed_defaults` 也不会把保存值重置。所以「重启」并非本问题的根因。

---

## 3. 根因分析

### 3.1 核心结论

「保存不生效」的本质是**消费方读错了源**：某配置项的写入目标是 DB，但运行时生效代码读的是 `.env`（`settings`）。由于 `settings` 是进程启动时从 `.env` 加载的静态对象，无论是否重启，它都**从不读取 DB 中的保存值**。

### 3.2 已确认的失效项清单

| 配置项 | 分组 | 保存目标（DB key） | 实际消费方 | 结论 |
|--------|------|--------------------|-----------|------|
| 允许注册 | security | `allow_registration` | `auth.py:272` 读 `settings.ALLOW_REGISTRATION` | ❌ 不生效 |
| 邮箱启用展示 | general/email | `email_enabled` | `system.py:65` 读 `settings.EMAIL_HOST is not None` | ⚠️ 展示不一致（次要） |

### 3.3 已排查确认为「无问题」的项（勿动，避免越界）

以下消费方均已正确通过 `get_config_value()` 读库，保存后即时生效，且重启后仍生效：

- 登录锁定/验证码/Token 过期：`security.py` 第 153、174、179-180、291、312 行
- 速率限制：`middleware/rate_limit.py` 第 48、53 行
- 合规阈值 / `block_time` 封锁时长：`compliance_service.py` 第 352、405-407、589、1262、1406、2078、2487 行
- 调度任务间隔：`main.py` 各任务循环（`_get_scheduler_interval` 读库）及 `arp_collector_service.py` 第 426 行
- 告警阈值：`main.py` 第 564 行、`compliance_service.py` 第 687 行
- `debug` / `log_level` / `environment`：DB 端 `is_readonly=True`，前端本就不可编辑，读 `.env` 合理
- `terminal_service.py:219` 的 `self.sangfor = SangforService()`：死代码，全局默认防火墙未实际使用（真实封锁按 `_get_sangfor_service_by_tag` 走数据源配置）

## 4. 修复方案

### 4.1 核心修复：允许注册改为读库

文件：`backend/app/api/v1/endpoints/auth.py`

当前（第 271-276 行）：

```python
# Check if registration is allowed
if not settings.ALLOW_REGISTRATION:
    raise HTTPException(
        status_code=status.HTTP_403_FORBIDDEN,
        detail="Public registration is disabled. Contact an administrator to create an account."
    )
```

改为读库（`get_config_value` 按 default 的 bool 类型解析，DB 存 "true"/"false" 字符串）：

```python
# Check if registration is allowed (hot-reloadable, DB-backed with .env fallback)
from app.services.config_service import get_config_value
allow_registration = await get_config_value("allow_registration", settings.ALLOW_REGISTRATION)
if not allow_registration:
    raise HTTPException(
        status_code=status.HTTP_403_FORBIDDEN,
        detail="Public registration is disabled. Contact an administrator to create an account."
    )
```

> `register` 端点已有 `db: AsyncSession = Depends(get_db)`，但使用模块级 `get_config_value` 更简单——它内部自行开一个 DB session 兜底，无需依赖已有 `db` 参数。

### 4.2 次要与可选（需你确认是否一并处理）

`system.py:65` 的 `/system/config` 端点将 `email_enabled` 返回为 `settings.EMAIL_HOST is not None`，与 DB 中可编辑的 `email_enabled` 可能不一致。若该返回值被前端用于展示邮箱开关状态，应改为读库：

```python
from app.services.config_service import get_config_value
...
"email_enabled": await get_config_value("email_enabled", settings.EMAIL_HOST is not None),
```

> 该端点当前依赖为 `Depends(get_current_user)`（无 db），同样使用模块级 `get_config_value` 即可。

## 5. 排查指引（辅助定位你遇到的具体项）

若你遇到的失效项不在 §3.2，可据此快速确认它是否同属「读错源」问题：

1. 查 DB 实际保存值：

```bash
docker exec tam_backend python -c "import asyncio; from app.core.database import async_session_factory; from app.models.system_config import SystemConfig; from sqlalchemy import select; \
async def m():\
    async with async_session_factory() as db:\
        r=await db.execute(select(SystemConfig));\
        [print(c.key,'=',c.value) for c in r.scalars().all()];\
asyncio.run(m())"
```

2. 在代码中搜索该 key 对应的消费方是否用 `settings.X` 而非 `get_config_value(key)`：

```bash
grep -rn "settings\." backend/app | grep -i "<关键字>"
```

3. 命中即属同类问题，修复方式同 §4.1：改为 `await get_config_value("<key>", settings.X)`。

## 7. 假设与决策

- **假设**：你的场景为「前端保存成功但功能行为未变」。若实为「数据库中的配置在重启后真的变回默认值」，则属另一类问题（数据库卷未持久化 / `manage.sh upgrade` 重置迁移），需另行排查 `docker-compose` 的 PostgreSQL 卷挂载——但基于当前代码审查，`seed_defaults` 不会覆盖已有 key，此假设概率低。
- **边界**：本计划仅修复已确认的失效项（`allow_registration` 为核心，`email_enabled` 展示为可选），**不**触碰 §3.3 中已验证正确的消费方，避免对功能正确的代码做无谓修改。
- **决策点**：§4.2 的 `email_enabled` 展示一致性修复是否纳入，待你确认。
