# 通知事件系统审计与修复计划

> 文档版本：v1.0  更新日期：2026-09-03

## 1. 摘要

对通知事件体系统一审计，聚焦四个维度：**事件缺失/重复、分类合理性、触发正确性、按渠道独立发送**。

结论：架构本身（`emit → Redis 队列 → worker → 规则/模板 → 多渠道发送 → 日志`）清晰，但存在 **4 类会导致通知丢失、重复或内容错乱的缺陷**，以及 **若干分类/事件定义的静态问题**。本计划按优先级提出修复方案。

### 缺陷总览（按严重度）

| # | 严重度 | 问题 | 影响 |
|---|--------|------|------|
| D1 | 高 | legacy 聚合器绕过整个通知管道 | `terminal.compliant / terminal.non_compliant / alert.policy_violation` 实际永远发不出（空 `EmailChannel(config={})` 无收件人），且不记账、不订阅、不走模板 |
| D2 | 高 | 重试忽略 `_channel_name` | 单渠道失败重试时会向**所有**订阅渠道重发 → 已成功渠道重复收到 |
| D3 | 高 | 发射器与调用点签名错乱 | `admin.role_changed / admin.config_changed / admin.permission_changed` 事件 data 内容错乱（传错字段） |
| D4 | 中 | 渠道 `send()` 返回类型不一致 | 为非 email 渠道定义模板后，worker 取 `result.success` 抛 `AttributeError`，投递恒失败 |
| D5 | 中 | 若干事件定义了却无触发点 | `system.datasource_sync_success`、`system.error/warning/alert`、`security.email_verified` 永不触发 |
| D6 | 低 | 分类/命名不一致 | `security.user_*` 归到 `admin` category；`alert.*` 与 enum 分组注释 `Compliance` 不符 |
| D7 | 低 | 重复/近似重复事件 | 自动封/解封同时发 `terminal.*` 与 `alert.auto_*`；不合规同时发 `terminal.non_compliant` 与 `alert.policy_violation` |

## 2. 现状分析

### 2.1 事件定义（共 35 个）

`event_types.py` 中 `EventType` 枚举 + `EVENT_METADATA` 共 **35 个事件**，分为 5 组：

- Terminal（6）：`terminal.compliant / non_compliant / blocked / unblocked / online / offline`
- Security（11）：`security.login_* / password_* / verification_code_sent / user_* / email_verified`（其中 `user_* / email_verified` 的 `category` 被标成 `admin`，见 D6）
- System（9）：`system.datasource_sync_* / firewall_connection_* / backup_* / error / warning / alert`
- Alert（6，enum 注释写 "Compliance events"）：`alert.compliance_rate_* / block_threshold / auto_block_triggered / auto_unblock_triggered / policy_violation`
- Admin（3）：`admin.config_changed / role_changed / permission_changed`

### 2.2 发送管道

`emit_event()`（[event_emitter.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/event_emitter.py)）→ `NotificationService.emit` → `NotificationWorkers.emit` 入队 `notify:queue:main` → `_main_worker` 弹队 → `_deliver_notification`（[notification_workers.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/notification_workers.py)）：按订阅匹配渠道 → 规则（[notification_rules.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/notification_rules.py)）→ 模板渲染（[notification_logging.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/notification_logging.py)）→ 渠道 `send()` → 日志/重试。

### 2.3 关键问题定位

- **D1**：`compliance_service.py:1785-1820` 用 `get_notification_aggregator().add_event()` 直发，绕过上述管道；`notification_aggregator.py:177` 又用无收件人的空 `EmailChannel(config={})` 发送，实际永远失败。`is_realtime_event/REALTIME_EVENT_TYPES`（event_types.py:312-333）在管道中**未被任何地方引用**，属死配置。
- **D2**：`notification_workers.py:377` 写入 `_channel_name`，但 `_deliver_notification`（244 行起）从未读取，重试时仍 `_get_subscribed_channels(event_type)` 重发全部订阅渠道。
- **D3**：见 §4.1。
- **D4**：webhook/feishu/dingtalk/wecom 的 `send()` 在 `subject and message` 分支返回 `dict`，否则返回 `NotificationResult`；worker 统一 `result.success`。
- **D5**：`emit_datasource_sync_success`、`emit_email_verified`、`emit_system_error/warning/alert` 仅定义、无任何调用点。

## 3. 修复方案

### 3.1 D3 —— 修复发射器调用签名错乱（高）

**语义约定**：现有 `emit_role_changed(username, changed_by, old_role, new_role)` 中 `username`=被变更对象、`changed_by`=操作者。roles.py 的 CRUD 是对"角色定义"而非"用户角色指派"，字段语义不匹配。

- `event_emitter.py` 的 `emit_role_changed`：改为 `(subject, changed_by, action, details)`，`details` 为可选 dict（承载 old_role/new_role 等）。
- 更新 4 处调用：
  - [auth.py:815](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/auth.py)（用户角色指派）：`emit_role_changed(user.username, current_user.username, "assigned", {"old_role": old_role, "new_role": new_role})`
  - [roles.py:159](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/roles.py)：`emit_role_changed(role.name, current_user.username, "created", {"description": role.description})`
  - [roles.py:230](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/roles.py)：`emit_role_changed(role.name, current_user.username, "updated", {"changes": changes})`
  - [roles.py:274](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/roles.py)：`emit_role_changed(deleted_name, current_user.username, "deleted", {})`
- `emit_config_changed(config_key, changed_by, old_value, new_value)` 保持签名，修复后方调用：
  - [settings.py:110-112](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/settings.py)：批量时按 `changes` 逐条发射
    ```python
    for c in changes:
        await emit_config_changed(c["key"], current_user.username, c.get("old_value"), c.get("new_value"))
    ```
  - [settings.py:144-145](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/settings.py)：改为 `emit_config_changed(key, current_user.username, old_value, update.value)`
- `emit_permission_changed(username, changed_by, permission, action)` 语义对齐：
  - [roles.py:232](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/api/v1/endpoints/roles.py)：`emit_permission_changed(role.name, current_user.username, "role_permissions", "updated")`

### 3.2 D2 —— 重试按渠道隔离（高）

`notification_workers.py`：
- `_deliver_notification` 开头读取 `payload.get("_channel_name")`；若存在，`subscribed_channels` 收敛为该单一渠道（重试只重发失败渠道）。
- 首次发送（无 `_channel_name`）保持现状，遍历全部订阅渠道。
- `retry_failed_notification`（[notification_service.py:561](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/notification_service.py)）手动重试已有 `_manual_retry/_log_id`，需保证不因新增 `_channel_name` 逻辑破坏；手动重试针对单条 log，应直接限定原 log 的 `channel_name`。

### 3.3 D4 —— 统一渠道 `send()` 返回类型（中）

统一约定：渠道 `send()` 在 `subject and message` 分支也返回 `NotificationResult`（而非裸 `dict`）。涉及 4 个文件：
- `webhook_channel.py`、`feishu_channel.py`、`dingtalk_channel.py`、`wecom_channel.py` 中 `send()` 的 `if subject and message:` 分支，将 `_send_*_text` 返回的 `{"success": ...}` 包装为 `NotificationResult`。

（`email_channel.py` 已返回 `NotificationResult`，一致。）

### 3.4 D1 —— 退役 legacy 聚合器直发路径（高）

- [compliance_service.py:1782-1820](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py) 删除 `get_notification_aggregator().add_event(...)` 直发，改为走发射器：
  - `terminal.compliant` → `emit_terminal_compliant(ip_addr, mac_addr)`
  - `terminal.non_compliant` → `emit_terminal_non_compliant(ip_addr, mac_addr, ["Non-compliant terminal detected"])`
  - （重复的 `alert.policy_violation` 一并去除，见 D7）
- `notification_aggregator.py` 整体为死代码/旁路：确认除 compliance_service 外无其他调用后，**删除该文件**（及 `get_notification_aggregator` 的所有 import）。
- `event_types.py` 中 `REALTIME_EVENT_TYPES` / `is_realtime_event` 为死配置：保留（避免影响事件元数据口径），但不再依赖其做聚合分流；如需分流逻辑后续单独设计。

### 3.5 D5 —— 补齐缺失触发点（中）

| 事件 | 处理 |
|------|------|
| `system.datasource_sync_success` | 在 [main.py:245-246](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py) 同步成功后补 `emit_datasource_sync_success(baseline.tag, baseline.tag, record_count)`（`record_count` 取 `sync_ipguard_data` 返回值，若该返回值不含条数则传 0） |
| `system.error / warning / alert` | 属通用兜底事件。若当前无对应业务场景，**从 `EVENT_METADATA` 移除**（避免 UI/前端出现永不触发的事件）；若需保留，在全局异常/健康检查处接入，本次默认移除 |
| `security.email_verified` | 当前无邮箱验证完成流程（仅验证码发送/2FA 校验），从 `EVENT_METADATA` 移除，保留枚举以防将来启用 |

> 说明：移除事件需同步考虑前端事件下拉/统计依赖；`get_event_types()` 与 `/notifications/events` 直接读 `EVENT_METADATA`，移除后自动不再展示。

### 3.6 D6 —— 分类与命名一致性（低）

- 将 `USER_CREATED / USER_DELETED / USER_UPDATED` 的 `category` 由 `admin` 改为 `security`（与字符串前缀 `security.user_*` 及 enum 分组一致）。
- 将 `EVENT_METADATA` 中 `alert.*` 六个事件的 `category` 保持 `alert`，同时把 enum 中 "# Compliance events" 注释改为 "# Alert events"（消除注释与命名矛盾）。

### 3.7 D7 —— 去重（低，需用户确认口径）

推荐口径（保留业务语义、减少重复打扰）：
- 自动封：保留 `terminal.blocked`（终端状态视角）与 `alert.block_threshold`（批量阈值视角），**移除** `alert.auto_block_triggered` 发射（[compliance_service.py:652](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py)）。
- 自动解封：保留 `terminal.unblocked`，**移除** `alert.auto_unblock_triggered` 发射（[compliance_service.py:984](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py)）。
- 不合规：保留 `terminal.non_compliant`，**移除**同路径的 `alert.policy_violation`（[compliance_service.py:1803-1809](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py)）。
- `alert.auto_*` / `alert.policy_violation` 的 `EventType`/`METADATA` 暂时保留（避免破坏既有规则/模板/迁移），仅停止发射。

> 若用户希望保留 `alert.auto_*` 作为独立告警级别，则 D7 不做删除，仅记录。

## 4. 假设与决策

1. 交付范围默认为 **审计 + 修复上述 7 项缺陷**（用户未明确选择"仅审计"）。
2. D1 采用"退役聚合器、改走发射器"方案（聚合器当前无法工作且绕过订阅/日志）。
3. D5 中 `system.error/warning/alert`、`security.email_verified` 默认**从 METADATA 移除**（无触发点则不在 UI 展示）。
4. D7 采用"去除重复发射、保留事件定义"的保守口径，避免影响既有规则/模板数据。
5. 所有修改遵循项目约束：不引入硬编码配置，服务重启/构建走 `manage.sh`，修改后需本地重建验证。

## 5. 验证步骤

1. **触发正确性**：`python -m compileall backend/app` 通过；针对 auth.py/roles.py/settings.py 发射调用做静态核对，确认传入字段与发射器签名一致。
2. **单元/集成验证**：
   - 创建/更新/删除角色、修改配置，观察 `admin.role_changed / config_changed / permission_changed` 日志 `details` 字段内容正确。
   - 触发一次 IPGuard 同步成功，确认 `system.datasource_sync_success` 入队并记录日志。
3. **按渠道独立发送**：配置 2 个渠道（如 email + webhook）订阅同一事件，人为让 webhook 失败：
   - 验证 email 仅发送一次（重试不再向 email 重发）。
   - 验证 webhook 进入 `retrying` → `failed` 状态，且 `NotificationLog.channel_name` 正确。
4. **合规事件不再丢**：触发一次合规状态变更，确认 `terminal.compliant / terminal.non_compliant` 经队列→订阅→渠道正常入队并记日志（不再走聚合器旁路）。
5. **模板渠道一致性**：为 webhook 定义模板后，确认投递成功（不再因返回 `dict` 抛错）。
6. **回归**：`/notifications/events` 展示事件列表与 `EVENT_METADATA` 一致；`/notifications/stats` 的 `event_coverage` 不再将已移除事件计入"永久未触发"。
