## 二、合法值域与状态机（客观判定标准）

### 2.1 字段值域
- `status` ∈ { `blocked`, `unblocked` }
- `compliance_status` ∈ { `compliant`, `bypass`, `non_compliant`, `unknown` }
- `block_state` ∈ { `NULL`, `no_firewall`, `block_failed` }
- `wl_match_type` ∈ { `NULL`, `mac`, `ip`, `both` }
- `source` ∈ { `arp`, `ipguard`, `whitelist`, `manual` }

### 2.2 状态机规则（来自 [auto_block_non_compliant](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L383-L713)）
- `non_compliant` + `status != blocked` → 触发封锁；
- 无防火墙绑定 → `block_state = 'no_firewall'`，不封锁（[L469-L481](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L469-L481)）；
- 有绑定但全部失败 → `block_state = 'block_failed'`（[L679](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L679)）；
- 至少一台成功 → `status = 'blocked'`、`block_state = NULL`、`firewall_tag` = 成功防火墙（多台以逗号拼接），按防火墙各写一条 Blacklist（[L563-L645](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L563-L645)）；
- 白名单命中（stale 场景）→ 自愈为 `bypass`，跳过封锁（[L432-L454](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L432-L454)）。

## 三、一致性断言（交叉验证清单）

### A. 状态机一致性（terminals 内部）
- A1 `compliance_status='bypass'` 的终端，`status` 必须是 `unblocked`（白名单永不封锁）。
- A2 `compliance_status='compliant'` 的终端，`status` 必须是 `unblocked`。
- A3 `block_state` 非空（`no_firewall`/`block_failed`）的终端，必须同时 `compliance_status='non_compliant'` 且 `status='unblocked'`。
- A4 `status='blocked'` 的终端，必须 `compliance_status='non_compliant'` 且 `block_state IS NULL`。

### B. 白名单一致性
- B1 `compliance_status='bypass'` 的终端，`wl_match_type` 应非空（有真实白名单匹配）。
- B2 `wl_match_type` 非空但 `compliance_status != 'bypass'` 的终端 → 可疑。
- B3 命中当前白名单的终端，其 `compliance_status` 应为 `bypass`（stale 检测）。

### C. 数据源与绑定一致性
- C1 `terminals.source_tag` 必须存在于 `data_sources.tag` 且 `type IN ('arp_ssh','arp_api')`。
- C2 上述数据源 `enabled = true`。
- C3 `terminals.firewall_tag` 指向的每个 tag 必须存在于 `data_sources.tag` 且 `type='sangfor'`，且与 `source_tag` 在 `data_source_bindings` 中存在绑定。
- C4 孤儿 `source_tag` / `firewall_tag`（指向不存在或已删的数据源）= 脏数据。

### D. 黑名单 ↔ 终端一致性
- D1 `blacklist` 活跃条目（`auto_unblocked=false AND unblocked_at IS NULL`）的 `ip_address`，应能对应到 `terminals` 中同 IP 的 `non_compliant`/`blocked` 终端；例外仅允许「防火墙有、DB 缺失」的对账补建条目（NULL-MAC）。
- D2 `terminals.status='blocked'` 的 IP，应至少对应一条活跃 Blacklist。
- D3 同一 IP 在多个 `firewall_tag` 各一条活跃记录 = 合法（各防火墙各一条，非重复）。
- D4 `block_state='no_firewall'` 的终端不应存在活跃 Blacklist。

### E. 统计口径自洽
- E1 `get_stats` 的 `total == compliant + bypass + non_compliant + unknown`（终端数，可加和）。
- E2 `non_compliant == non_compliant_blocked + non_compliant_unblocked`（终端数）。
- E3 `blacklist success_blocked(distinct IP) ≤ firewall_ip_count(各防火墙之和)`（同一 IP 多防火墙时后者更大，属正常）。

### F. 审计日志交叉验证
- F1 统计终端相关 action 计数：`auto_block_terminal` / `auto_unblock_terminal` / `firewall_block` / `firewall_unblock` / `compliance_status_changed` / `recalculate_compliance` / `whitelist_create|update|delete`（action 清单见 [grep 结果](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L696)）。
- F2 抽查最近 N 次封锁/解封，其 `details` 与当前 terminal/blacklist 状态可回溯对应。

## 四、取证查询清单（执行阶段，全部 SELECT 只读）

通过 `docker exec tam_db psql -U tam_admin -d tam_db -c "..."` 执行。以下为查询骨架，数字在执行阶段填入。

1. 基础分布：`SELECT compliance_status, status, block_state, count(*) FROM terminals GROUP BY 1,2,3 ORDER BY 1,2,3;`
2. 全组合交叉表（验证 A 类）：上述 GROUP BY 结果即为组合矩阵。
3. A 类矛盾项：
   - A1/A2：`SELECT ... WHERE compliance_status IN ('bypass','compliant') AND status='blocked'`
   - A3：`WHERE block_state IS NOT NULL AND (compliance_status <> 'non_compliant' OR status <> 'unblocked')`
   - A4：`WHERE status='blocked' AND (compliance_status <> 'non_compliant' OR block_state IS NOT NULL)`
4. B 类：`WHERE compliance_status='bypass' AND (wl_match_type IS NULL OR wl_match_type='')`；反向 `WHERE wl_match_type IS NOT NULL AND compliance_status <> 'bypass'`
5. C 类孤儿：
   - `terminals.source_tag NOT IN (SELECT tag FROM data_sources WHERE type IN ('arp_ssh','arp_api'))`
   - `terminals.firewall_tag` 拆分后不在 `data_sources.tag(type='sangfor')`
   - `source_tag` 与 `firewall_tag` 无 `data_source_bindings` 记录
6. D 类映射缺失：
   - 活跃 blacklist 的 IP 在 terminals 中无 `non_compliant` 终端
   - `status='blocked'` 的 IP 无活跃 blacklist
7. 数据源/绑定现状：`data_sources` 各 type/enabled 计数、`data_source_bindings` 列表。
8. `whitelist` 各 `pattern_type` 计数。
9. `audit_logs` 按 `action` 计数 + 最近 20 条终端相关日志（`resource_type IN ('terminal','blacklist','firewall')`）。

## 五、异常归类（输出报告时使用）

- **硬矛盾（必须修）**：违反 A1/A2/A3/A4、C1/C2/C3 的状态组合/孤儿标签——状态机被破坏或数据源被删导致。
- **数据漂移（需关注但不立即阻塞）**：B3 stale（命中白名单却非 bypass）、D1/D2 映射缺口（对账待补/漏封锁）。
- **合法中间态（正常，用于说明口径）**：`non_compliant + unblocked + block_state IN (no_firewall, block_failed, NULL)`。
- **口径说明项**：D3 同一 IP 多防火墙多条、E3 distinct IP vs 防火墙之和的差值。

## 六、输出报告（客观、只列真实数字）

1. 各类状态/标签的**真实计数表**（来自查询结果）。
2. 逐条断言（A–F）的**通过/失败 + 命中条数**，命中者附**样例 IP/MAC 明细**（仅真实查询命中的记录）。
3. 异常清单按「硬矛盾 / 数据漂移 / 合法中间态 / 口径说明」分类。
4. 明确标注：**未命中某项 = 该项为 0 条，不编造样例**。
