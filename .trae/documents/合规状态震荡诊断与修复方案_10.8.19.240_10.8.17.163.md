# 合规状态震荡诊断与修复方案（10.8.19.240 / 10.8.17.163）

## 一、摘要

本方案针对两台终端（10.8.19.240、10.8.17.163）在 MAC 未变化的情况下合规状态反复震荡的现象，以及 10.8.19.240 被判为非合规却显示 "BOTH" 的问题，先通过代码定位出机制层面的根因假设，再以只读方式连库拉取真实轨迹进行确认，最后给出修复建议（本次仅出诊断报告与修复方案，不立即改动代码）。

**只读连库已确证的关键事实（v1.1）：**

1. **10.8.19.240 —— "BOTH" 是前端误导，真实不合规因素是 IP**：
   - 终端 MAC `28-D0-EA-D3-60-C6` 在 IPGuard 基线中确实存在，但它绑定在 IP `192.168.3.62` 上（**不是** 10.8.19.240）；IP `10.8.19.240` 本身**不在**基线中。
   - 因此 `_match_ipguard_in_memory` 返回 `ip_found=False, mac_found=True` → 判 non_compliant，黑名单 `reason` 正确写为 `"IP 不合规，MAC 合规"`（黑名单条目 id=3789）。
   - 前端 [Terminals.tsx](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Terminals.tsx#L207-L216) 的 `black_match_type` 因为该终端的 IP 和 MAC **都出现在同一条黑名单记录**里而算成 `both`，于是 non_compliant 徽标旁显示 `(BOTH)`，与"IP/MAC 哪个不合规"无关。
2. **10.8.17.163 —— IP、MAC 确实在基线且为同一配对，但 IPGuard 命中会周期性翻转为 False**：
   - 当前基线缓存存在精确配对 `10.8.17.163 → C8-B2-9B-87-CC-D3`（同一条目，IPGuard 来源为 `mssql 10.8.80.26:1433/OCULAR3`）。
   - 后端日志显示同一终端在 15:14 判 `ipguard=False`（降级 non_compliant），10 分钟后的 15:24 又判 `ipguard=True`（升级 compliant），即 `ig_match` 在相邻周期内反复翻转。
3. **震荡的直接闭环是"封锁失败 → 静默回滚 compliant"**：
   - [_apply_compliance_result](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2036-L2055) 在"首次降级但所有防火墙封锁都失败"时，会把 `compliance_status` **静默回滚为 old_compliance（compliant）**，且**不写 `compliance_status_changed` 审计事件**；于是 10 分钟后又被重新检出 non_compliant，形成 `compliant → non_compliant → (静默)compliant → …` 周期。
   - 封锁失败在审计日志里表现为 `firewall_block` 的 `success=false`、`Blocked 0, skipped 0, errors 1`，即 Sangfor `whiteblacklist` 接口对封禁返回非 0 错误码。
4. **防火墙侧存在额外异常**：Redis `reconcile:latest`（08:14）显示防火墙 `af` 返回 `firewall_ip_count=0`，而 DB 有 300 条活跃黑名单，说明防火墙曾被**外部清空**（对账服务保守跳过未回写），这是 08:14 前后反复封锁失败的背景。

## 二、现状与代码分析

### 2.1 "BOTH" 标签的真实来源（误导点）

- 前端合并逻辑：终端分别计算 `macInBlacklist`（按 MAC）与 `ipInBlacklist`（按 IP），两者都命中则 `black_match_type='both'`，只命中一个则 'mac'/'ip'。
- non_compliant 徽标旁显示 `black_match_type.toUpperCase()`，因此被封锁的终端（封锁时 [compliance_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L618-L627) 同时写入 ip 和 mac 到黑名单）几乎恒显示 "BOTH"。
- 真实的不合规因素其实已计算并写入黑名单 `reason` 字段（如 `"IP 不合规，MAC 合规"`），但没有作为结构化字段暴露给前端。

### 2.2 合规判定逻辑（为什么 10.8.19.240 MAC 在基线仍不合规）

- `_match_ipguard_in_memory` 返回 `(is_compliant, ip_found, mac_found)`：
  - 仅当存在 `entry_ip == ip_address` 且 `entry_mac == 归一化MAC`（或 IP 命中 + `mac_prefix_ipguard` 命中）时返回 `(True, True, True)`。
  - 仅 `entry_mac == 归一化MAC` 时置 `mac_found=True`，但最终 `is_compliant=False`。
- 结论：10.8.19.240 "IP 不在基线" 是一个硬伤，即使 MAC 在基线也会判 non_compliant；其 blacklist.reason 应当为 "IP 不合规，MAC 合规" 而非 "都不合规"，但前端 `black_match_type` 却显示 "BOTH"，于是产生困惑。

### 2.3 震荡机制

- **终端唯一定义**：`terminals.mac_address_normalized` 唯一约束（[terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L48-L52)），IP 是可变属性，DHCP 换 IP 会更新同一行并置 `ip_changed_at`。
- **IP 变更副作用**：换 IP 时清零 `compliant_confirm_count` 与 `non_compliant_confirm_count`（[arp_collector_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/arp_collector_service.py#L321-L323)），使"连续确认"抗震荡机制无法跨 IP 周期累积。
- **宽限期**：IP 变更后 10 分钟内 (`compliance_ip_grace_minutes`) 不降级（[recalculate_all_compliance](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2163-L2171)），期间状态冻结。
- **确认阈值**：升级/降级均需连续 `compliance_confirm_threshold`（默认 2）次一致判定（[compliance_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2188-L2251)）。
- **IPGuard 陈旧保护**：缓存 `last_sync_at` 超过 12 分钟时，本周期阻断 non_compliant 降级方向（[compliance_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2114-L2116)）。
- **同 MAC 多 IP 采集**：ARP 采集在同批内按 MAC 去重、只保留**首个** IP（[arp_collector_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/arp_collector_service.py#L294-L297)）。若同一 MAC（桥接/虚拟机）被报出多个 IP，且每次扫描顺序不同，终端 IP 会在多值间抖动，直接触发上述整套机制。

### 2.4 关键配置默认值（可被系统设置覆盖）

| 配置键 | 默认 | 作用 |
| --- | --- | --- |
| `compliance_confirm_threshold` | 2 | 连续确认次数阈值 |
| `compliance_ip_grace_minutes` | 10 | IP 变更宽限期 |
| `compliance_cooldown_minutes` | 10 | 封锁/解封冷却期 |
| `ipguard_stale_threshold_minutes` | 12 | IPGuard 缓存陈旧阈值 |
| `compliance_whitelist_miss_threshold` | 6 | 白名单缺失降级阈值 |

| `cache_ipguard_ttl` | 900 | IPGuard 缓存 TTL（秒） |

## 四、确诊结论（已连库确证）

| 现象 | 确诊根因 | 证据 |
| --- | --- | --- |
| 10.8.19.240 显示 "BOTH" | 前端 `black_match_type='both'`（IP+MAC 都在黑名单），与"IP/MAC 哪个不合规"无关 | 黑名单 id=3789 同时含 ip=10.8.19.240 与 mac=28-D0-EA-D3-60-C6，`reason="IP 不合规，MAC 合规"` |
| 10.8.19.240 MAC 在基线仍不合规 | `_match_ipguard_in_memory` 仅"IP 同条目命中"或"IP+MAC 同条目命中"才合规；该 MAC 绑定在 `192.168.3.62`，IP `10.8.19.240` 不在基线 | Redis `ipguard:ipguard` 中 `192.168.3.62 → 28-D0-EA-D3-60-C6` |
| 10.8.17.163 IP+MAC 都在基线仍震荡 | IPGuard 命中在相邻周期翻转：15:14 `ipguard=False` → 15:24 `ipguard=True`（源数据/配对瞬时缺失后恢复） | 后端日志 `CONFIRMED downgrade ... ipguard=False`、`CONFIRMED upgrade ... ipguard=True` |
| 反复"封锁失败" | Sangfor `whiteblacklist` 接口对封禁返回非 0 错误码（`Blocked 0, skipped 0, errors 1`） | 审计 `firewall_block success=false`；`reconcile:latest` 显示防火墙曾被外部清空（0 IP） |
| 震荡闭环 | 首次降级 + 封锁失败 → [_apply_compliance_result](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2036-L2055) 静默回滚为 compliant（不写审计）→ 10 分钟后再检出非合规 | 审计仅见 `compliant → non_compliant`（无反向事件），周期约 10 分钟 |

## 五、修复方案（建议，本次不实施）

### 5.1 修复 "BOTH" 标签误导（对应 10.8.19.240 的疑问）

**目标**：让 non_compliant 徽标旁的标记反映**不合规因素**：`IP`（仅 IP 不合规）/ `MAC`（仅 MAC 不合规）/ `BOTH`（IP 和 MAC 都不合规）。

- 后端：给 `terminals` 新增结构化字段 `non_compliant_type`（VARCHAR(10)，可空，取值 `ip|mac|both`）。
  - 变更点：[terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py#L18-L52) 加列 + Alembic 迁移。
  - 写入点：[_apply_compliance_result](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L1680-L1701) 已计算 `ip_found/mac_found`，直接映射：
    - `not ip_found and not mac_found` → `both`
    - `not ip_found and mac_found` → `ip`
    - `ip_found and not mac_found` → `mac`
    - `use_ip_only` 场景固定为 `ip`
  - 转为 compliant/bypass 时清空为 NULL。API 序列化补充暴露该字段。
- 前端：non_compliant 徽标旁用后端 `non_compliant_type` 展示（IP/MAC/BOTH），替代现有 `black_match_type`；`black_match_type` 继续保留用于黑名单解除时的标识符选择（IP/MAC）。

### 5.2 抑制震荡（按确诊结论给出针对性建议）

1. **消除"封锁失败静默回滚"造成的周期性假翻（最高优先级，两终端都受影响）**：
   - 现状：[compliance_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2036-L2055) 在首次降级且封锁全失败时，把 `compliance_status` 静默改回 `old_compliance` 且不写审计事件。
   - 建议：回滚时保留 `block_state='block_failed'` 并**显式写一条审计事件**（或维持 non_compliant + block_failed 而非回滚为 compliant），避免"真 non_compliant 终端被强行标成 compliant、下周期又翻转"；同时阻断同一 MAC 在冷却期内的二次降级。
   - 影响面：改变封锁失败后的中间态语义，需同步核对 `block_failed`/`no_firewall` 统计口径与前端展示。
2. **定位 10.8.17.163 的 IPGuard 源数据为何在 15:14 缺失、15:24 恢复**：
   - 排查 IPGuard `OCULAR3`（10.8.80.26）中该终端 `AGT_IP_MAC_STR` 是否在同步边界出现"同 MAC 多 IP / 同 IP 多 MAC / 记录瞬时滞后"，以及 sync 是否偶发失败却未落到 backup 缓存。
   - 建议：sync 失败时优先使用 `ipguard:backup:<tag>` 兜底而非置空；对齐 `scheduler_ipguard_sync_interval`、`cache_ipguard_ttl` 与 `ipguard_stale_threshold_minutes`，避免"新鲜但缺配对"的窗口被当作合规证据。
   - 影响面：影响合规计算的数据新鲜度与误判方向。
3. **修复防火墙侧异常（外部清空未回写）**：
   - 排查 Sangfor `af` 白黑名单为何被外部清空（`reconcile:latest` 0 IP vs DB 300 条）；确认封禁接口返回非 0 错误码的具体 `message`，判定是"接口故障"还是"资产冲突/被人工清空"。
   - 影响面：涉及对账服务是否允许回写，需产品确认"防火墙实际状态为权威"的既有决策。
4. **IP 漂移 / 同 MAC 多 IP 收敛（若第 2 条进一步确认 IP 在抖动）**：
   - 调整 [arp_collector_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/arp_collector_service.py#L294-L324) 同 MAC 多 IP 收敛策略，优先保留与上一周期一致的 IP，减少 `ip_changed_at` 反复刷新。
   - 影响面：需回归 DHCP 正常换 IP 识别场景。
