# 统计卡片简化与黑名单口径对齐方案

> 文档版本：r1  更新日期：2026-09-01

## 一、概述（Summary）

针对本轮反馈，做两处收敛，均只做减法、不新增任何统计维度：

1. **终端管理「非合规」卡片**：只保留「非合规终端总数」一个数字，删除「非合规已封锁 / 非合规待封锁」的次级拆分。具体封锁状态（blocked/unblocked）由页面现有的「状态」筛选条件自行过滤，卡片不再承担拆分职责。
2. **黑名单管理卡片**：
   - 删除「防火墙实际封锁（Firewall Actual Blocks）」卡片，与「成功封锁（Successfully Blocked）」合并为一个概念；
   - 修正「成功封锁」卡片数字与下方列表实际条目数不一致的问题（二者应对齐）。

## 二、现状分析（Current State）

### 2.2 黑名单三组数字互相打架

当前黑名单页存在三个语义上「应该相等」却各自不同的数字（均为真实查询结果）：

| 数字 | 来源 | 当前值 |
| --- | --- | --- |
| 「成功封锁」卡片 `success_blocked` | `count(DISTINCT ip_address)`（活跃黑名单） | **277** |
| 「防火墙实际封锁」卡片 `firewall_ip_count` | `reconcile:latest` 缓存 | **276** |
| 下方列表实际条目数（默认 active） | `count(Blacklist.id)`（活跃黑名单，原始行数） | **278** |

根因：

1. [get_blacklist_stats](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1637-L1642) 的 `success_blocked` 用 `count(DISTINCT ip_address)` 去重计数，而 [get_blacklist_count](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1607)（列表总数）用的是 `count(Blacklist.id)`（原始行数）。两者对「成功封锁」的口径不一致，导致卡片数字（277）≠ 列表条目数（278）。
2. `firewall_ip_count`（276）是防火墙对账后的实际封锁 IP 数，与「成功封锁」本质是同一概念，额外曝光反而制造困惑。

> 说明：`277 vs 278` 差 1，源于 IP `10.8.24.177` 存在两条活跃记录（对应两个不同 MAC：`F8E43B9CBD0C` / `668AE2326C20`）。这是「同一 IP 被不同终端先后占用且均未解封」的真实场景，列表按「黑名单条目」展示两条、按 IP 去重后是一条，属正常，非脏数据。

## 四、假设与决策（Assumptions & Decisions）

1. **「成功封锁」= 活跃黑名单条目行数**。它直接对应下方列表实际展示的条目，是对齐后的唯一口径。
2. **`get_stats` 的 `blocked` 字段保持 `count(DISTINCT ip)` 不变**（项目既定口径，用于看板「已封锁 IP 数」），本次不改。
3. **`firewall_ip_count` 仅从黑名单统计卡片剥离**。对账核心（`firewall_reconciliation_service.py`）、对账接口（`backend/app/main.py`）、独立脚本（`trigger_reconcile.py`）、系统设置页（`GeneralSettings.tsx` 直接读对账结果）继续保留该字段，不受影响。
4. **`non_compliant_unblocked` 全量移除**（后端字段 + 前端类型 + i18n），因为拆分删除后它无任何使用处。
