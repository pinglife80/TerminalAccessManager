# 数据状态一致性问题根治方案

> 文档版本：v3.17.3  更新日期：2026-08-31
> 目标：「对齐统计口径」+「根治 non_compliant+unblocked 中间态」
> 决策：无防火墙终端采用**透明化标记**；新增 **Terminal.block_state 字段 + 037 迁移**

---

## 一、摘要

用户反馈三个长期无法消除的现象：

1. Dashboard / 终端管理 / 黑名单管理中「非合规且封锁」的统计**总与防火墙实际封锁数对不上**；
2. 终端管理页存在**大量 non_compliant + unblocked（非合规未封锁）**终端；
3. 黑名单管理页**总是有大量 Block Pending Retry** 终端。

经代码审查确认，这三个现象是**同一个根因群**的三种表现，可以一次性根治：

- **统计口径混淆**：系统把「三个本质不同的对象」强行对齐，却又在前后端口径上不一致。
- **中间态无出口**：`non_compliant + unblocked` 是合规状态机的「合法残留态」，但**没有可区分、可收敛的标记**，导致它永久性堆积并被重复计入「Block Pending Retry」。

本方案通过 **① 统一并显式化统计口径** + **② 为中间态引入 `block_state` 字段实现透明化与收敛**，彻底消除上述表象。

---

## 二、现状根因分析

### 2.1 三个统计对象的本质差异（对不上的根本原因）

系统中「封锁数」实际存在**三个不同对象**，从设计上就永远不可能相等：

| 指标 | 数据来源 | 统计对象 | 去重方式 | 包含内容 |
|------|---------|---------|---------|---------|
| `blocked`（Dashboard / 终端页「非合规」卡） | `Blacklist` 表 | 活跃黑名单 IP | `COUNT(DISTINCT ip_address)` 跨防火墙去重 | 自动封锁 + 手动封锁 + 对账补建 NULL-MAC 条目（可能无对应终端），**不过滤来源** |
| `non_compliant`（Dashboard） | `Terminal` 表 | 终端行 | 按终端（MAC 归一化） | `compliance_status=non_compliant` **且** `status=blocked`，**仅启用 ARP 源** |
| `firewall_ip_count`（防火墙实际） | `reconcile:latest` 缓存 | 防火墙封锁 IP | **按防火墙累加，不跨防火墙去重** | 含外部直接封锁、多防火墙重复计数 |

三者对不上的结构性原因：

- `blocked` 含**手动封锁**与**对账补建的 NULL-MAC 条目**（这些无终端记录），`non_compliant` 不含；
- `firewall_ip_count` 是**每台防火墙封锁 IP 数之和**，多防火墙环境同一 IP 会被重复计数；`blocked` 是跨防火墙 distinct；
- `non_compliant` 只统计「已封锁」的终端，而 `non_compliant+unblocked` 的中间态终端被排除在外。

**关键代码证据**（[terminal_service.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py)）：

- [get_stats L286-296](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L286-L296)：`blocked` = `COUNT(DISTINCT Blacklist.ip_address)` 活跃条目；
- [get_stats L298-309](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L298-L309)：`non_compliant` = `non_compliant AND status=blocked` 的终端行；
- [get_blacklist_stats L1624-1629](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1624-L1629)：`success_blocked` = `COUNT(DISTINCT Blacklist.ip_address)`。

### 2.2 前端口径错位（加剧「对不上」的感知）

- [Terminals.tsx L432](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Terminals.tsx#L430-L433)：`blockedCount = stats?.blocked`，却把它的数值放进了标题为「非合规」的卡片（[L741-742](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Terminals.tsx#L736-L743)）。即「非合规卡」实际显示的是「黑名单 IP 数」而非「非合规终端数」。
- [Blacklist.tsx L166-244](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/frontend/src/pages/Blacklist.tsx#L166-L244)：仅有 5 张卡（success_blocked / pending_retry_block / success_unblocked / pending_retry_unblock / firewall_errors），**没有「防火墙实际封锁数」卡片**，用户无法把「数据库口径」与「防火墙口径」并排对比。
- `get_blacklist_stats` 返回值**不含 `firewall_ip_count`**（缓存 `reconcile:latest` 里有，但未吐出）。

### 2.3 中间态 non_compliant+unblocked 无法闭环（Block Pending Retry 积压根因）

`pending_retry_block` 统计口径 = `non_compliant + unblocked`（启用 ARP 源），见 [get_blacklist_stats L1634-1648](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/terminal_service.py#L1634-L1648)。

该中间态有两条产生路径，其中一条**永远无法收敛**：

**路径 A（永久积压，根治目标）——无绑定防火墙**

- 合规重算降级为 non_compliant 但 ARP 源未绑定任何防火墙时，[_apply_compliance_result L1896-1900](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L1896-L1900) 直接置 `status=unblocked`，但**保留 `compliance_status=non_compliant`**；
- 调度器 retry-block 遇到无防火墙时 [main.py L433-435](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py#L433-L435) 直接 `continue` 跳过；
- `auto_block_non_compliant` 无防火墙时 [compliance_service.py L469-476](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L469-L476) 直接返回 skipped，不落地任何状态。

结果：这些终端**永远是 `non_compliant + unblocked`**，每次统计都被计入 Block Pending Retry，但永远无法被封锁，形成永久 backlog。

**路径 B（可恢复但缺标记）——有防火墙但封锁失败**

- [main.py L456-457](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py#L429-L477)：`all_success` 为假时不设置任何标记，终端继续留在 `non_compliant + unblocked` 待下一轮重试；
- [_apply_compliance_result L2024-2030](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/compliance_service.py#L2024-L2030)：首次降级封锁全失败会回滚 `compliance_status`（行为正确），但「已是 non_compliant 的重试失败」与「首次降级失败」两种语义混在同一个 `else` 分支，无独立标记。

> 附带注意：`_repair_stale_terminal_status`（[firewall_reconciliation_service.py L183-228](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/services/firewall_reconciliation_service.py#L183-L228)）会把「无活跃黑名单背书的 blocked 终端」重置为 unblocked；若该终端仍是 non_compliant，也会落入中间态而不留标记。

## 三、统计口径对齐方案（目标态定义）

修复后，系统统一暴露并清晰标注**四类互不混淆的数值**：

| 新/旧 | 字段 | 定义 | 采集对象 |
|------|------|------|---------|
| 沿用 | `blocked` | 活跃黑名单**去重 IP 数**（含手动 + 对账 NULL-MAC） | Blacklist |
| 沿用 | `non_compliant` | `non_compliant + status=blocked` 的**终端数**（action-state 一致） | Terminal |
| 新增 | `non_compliant_unblocked` | `non_compliant + status=unblocked` 的**终端数**（中间态总量） | Terminal |
| 新增 | `firewall_ip_count` | **防火墙实际封锁 IP 数**（每台累加，标注口径） | reconcile 缓存 |

前端按此定义在卡片标题/副标题中**明确口径**（「已封锁 IP」「非合规已封锁终端」「待封锁终端」「防火墙实际封锁」），从根本上避免「同一张卡、不同对象」的错乱。

## 四、改动方案

### 4.1 模型与迁移（新增 block_state 字段）

**文件：[models/terminal.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/models/terminal.py)**

在 `Terminal` 模型新增字段：

```python
block_state = Column(String(30), nullable=True, index=True)
# None          -> 正常（已封锁 或 不适用）
# 'no_firewall' -> non_compliant 且 ARP 源无绑定防火墙（不可封锁，永久积压标记）
# 'block_failed'-> non_compliant 且封锁失败（可恢复，等待 retry-block）
```

**文件：新增 [037_terminal_block_state.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/alembic/versions/037_terminal_block_state.py)**


**文件：[main.py](file:///home/dada/Codespace/TraeCN/TerminalAccessManager/backend/app/main.py)**

## 五、假设与决策

1. **`non_compliant` 语义保持不变**：仍意为「非合规且已封锁」（action-state 一致性），不扩展到全部非合规终端；中间态通过新增 `non_compliant_unblocked` 与 `block_state` 暴露。
2. **无防火墙终端保留 non_compliant 标签**（透明化标记，非源头阻断）：它们仍被如实标记为「不合规」，只是显式区分「不可封锁」原因，避免占用 Block Pending Retry。
3. **历史数据无一次性回填迁移**：`block_state=NULL` 由调度器首轮 retry-block 自动回填；统计查询对 NULL 兜底归入「可重试」类，保证不丢历史中间态。
4. **不改变现有三层防震荡、冷却期、白名单权威预检等逻辑**，仅在与封锁落点相关的分支叠加 `block_state` 标记。
