## 三、计划步骤

### 第 0 步：提交前本地验证（可选但推荐）

```bash
# 后端 lint + 测试
cd backend && ruff check app/ && python -m pytest tests/ -q

# 前端 lint + 测试
cd frontend && npx eslint . --ext ts,tsx --max-warnings 25 && npx vitest run
```

> 本项目统一入口：`./manage.sh test`（如需，则以 manage.sh 为准替代上述命令）。

### 第 1 步：将 `.trae/` 重新纳入版本控制

1. 编辑 `.gitignore`，删除第 83-84 行：

```gitignore
# Trae IDE workspace
.trae/
```

2. 暂存并提交：

```bash
git add .gitignore .trae/
git commit -m "chore(repo): re-include .trae workspace planning docs into version control"
```

> 说明：移除 `.trae/` 忽略规则后，`git add .trae/` 会将所有此前被忽略的 `documents/`、`specs/` 计划文档纳入跟踪；本计划文件本身也会被一并纳入。

### 第 2 步：功能代码提交（develop，Conventional Commits）

分两个逻辑提交，后端与前端分离：

```bash
# 1) 后端：可配置封锁时长
git add backend/app/services/config_service.py \
        backend/app/schemas/system_config.py \
        backend/app/services/compliance_service.py \
        backend/app/services/firewall_reconciliation_service.py
git commit -m "feat(compliance): make blacklist block_time configurable via system settings"

# 2) 前端：设置页 + 自动封锁弹窗下拉
git add frontend/src/hooks/useTerminalData.ts \
        frontend/src/pages/GeneralSettings.tsx \
        frontend/src/components/datasources/ComplianceBaselinesTab.tsx
git commit -m "feat(frontend): add block_time dropdowns to settings and auto-block modal"
```

### 第 3 步：文档内容更新 + 版本号递增

按「四、文档变更明细」编辑文件：

1. `VERSION`：`3.14.0` → `3.15.0`
2. `docs/changelog.md`：文档头版本号 + 新增 `[3.15.0]` 条目
3. `docs/release-notes.md`：文档头版本号 + 新增 `[v3.15.0]` 发布记录
4. `docs/production-readiness-assessment.md`：版本跟踪表新增 v3.15.0 行
5. `docs/business-workflow.md`：文档头版本号 `v3.14.0` → `v3.15.0`（正文修改已在工作区完成）

随后提交为发布提交：

```bash
git add VERSION \
        docs/changelog.md \
        docs/release-notes.md \
        docs/production-readiness-assessment.md \
        docs/business-workflow.md
git commit -m "chore(release): bump version to v3.15.0 and refresh docs"
```

### 第 4 步：推送 develop

```bash
git push origin develop
```

> 推送会触发 CI（lint/test/build）。确认 4 项关键 status check 通过。

### 第 5 步：手动 PR（develop → main）

在 GitHub 上创建 Pull Request：

- Base：`main` ← Compare：`develop`
- 标题建议：`release: v3.15.0 黑名单封锁时长可配置`
- 描述：粘贴 `docs/changelog.md` 中 `[3.15.0]` 条目内容
- 等待 CI（`backend-lint`/`backend-test`/`frontend-lint`/`frontend-test`）全部通过
- 自审 diff 后选择 **Merge**（不 squash、不删除 develop）

### 第 6 步：打 tag

PR 合并后（`main` 已含 v3.15.0 内容，且满足「仅 PR 合并后可打 tag」约束）：

```bash
git checkout main
git pull origin main
git tag -a v3.15.0 -m "release v3.15.0: configurable blacklist block_time"
git push origin v3.15.0
```

### 第 7 步：同步 develop

```bash
git checkout develop
git merge main
git push origin develop
```

> 因 develop 的 tip（发布提交）是 main 合并提交的祖先，此步骤通常为 fast-forward，develop 与 main 收敛到同一点。

### 第 8 步（可选）：GitHub Release

在 GitHub 上基于 tag `v3.15.0` 创建 Release，Release notes 从 `docs/changelog.md` 的 `[3.15.0]` 条目复制。

## 五、假设与决策

1. **发布版本号取 Minor（v3.15.0）**：本次变更主体是「向后兼容的新能力」（用户可配置封锁时长），含一处伴随性 bug 修复，符合语义化版本 Minor 递增规则（git-workflow-guide §2）。若用户倾向按 Patch（v3.14.1）处理，需将全部 v3.15.0 字样统一替换。
2. **发布时间戳统一为 `2026-08-25`**（当前本地日期）。
3. **走「直接提交 develop + 发布 PR」流程**：沿用本项目 v3.13.0/v3.14.0 的实际做法（特性提交直接在 develop，发布经 develop → main 的 PR），而非为本次特性再开 feature 分支；「手动 PR」即 develop → main 发布 PR。
4. **`.trae/` 重新纳入版本控制**：移除 `.gitignore` 中的 `.trae/` 规则，将当前全部计划/规格文档（`documents/`、`specs/`）重新纳入跟踪并提交推送，作为独立 `chore(repo)` 提交。
5. **`frontend/package.json` 的 `version`（现为 3.12.1）不手动修改**：依据项目约束，Docker 构建时从 `VERSION` 同步到 `package.json`，不属于发布人工步骤。
6. **`docs/release-plan.md`、`README.md` 不纳入本次同步**：v3.14.0 发布提交未触碰它们，非每次发布的必更文档。
7. **业务链/构建验证已在前序会话完成**：前端 tsc/vite 构建通过、后端容器指纹已核对 4 处代码变更、启动日志 `Seeded config: block_time = 30d` 已确认；本计划聚焦版本/文档/流程动作，不重复实现代码。
